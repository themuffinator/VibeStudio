# Package Manager

VibeStudio browses folders, PAK, Doom/texture WAD, ZIP, and PK3 packages. Editing
builds a staging plan; source files remain unchanged until a requested save.
Generated assets, imported files, compiled map output, and dependency exports use
the same package services as the CLI.

Package menus and toolbars share command availability. Opening, saving, staging
and extraction disable conflicting package controls until the work completes,
fails or is cancelled. The Open Package, Open Folder Package and Open Draft
commands become available again afterward. Changing the selected entry or folder
updates package controls without resetting unrelated studio selections.

For prepared Quake-family builds, **Build > Publish Prepared Build** reviews the
captured package/draft assets with the verified BSP, generated shaders and
external lightmaps. It uses the same deterministic PAK/PK3 writers and atomic backup
publisher, with optional build-source inclusion. Failed or changed outputs cannot
publish; **Open Prepared Assets** remains available for general browsing/editing.
**Deploy Prepared Build** writes that complete PK3 into a reviewed installation
folder using the same publisher. It checks the reviewed destination hash, retains
a backup on replacement and requires one-operation permission for read-only
installations. Optional launch follows verified publication. CLI equivalents are
`build artifacts`, `build publish-prepared`, `build deploy-plan` and
`build deploy-prepared`. See
[Prepared Builds](LEVEL_EDITOR.md#prepared-builds-with-current-assets).
Quake and Quake II publish PAKs through the same writer and backup service;
Quake `.lit`/`.lux` ship with the BSP, while compiler metadata stays in the
workspace. The optional source bundle includes the generated Quake WAD.
PAK path and size limits remain enforced. Deployment is Quake III-only.

Levels can stage reusable `.vprefab` assemblies as owned generated bytes.
Open a prefab entry, including a pending addition, to preview and insert it in
the current Quake-family map. Map insertion and package staging keep independent
undo/save histories. A prefab retains relative material, model and sound paths;
its dependency review uses the same archive/staged reader. Export the referenced
assets alongside the prefab when sharing a library. See
[Reusable Prefabs](LEVEL_EDITOR.md#reusable-prefabs) for the complete workflow.

`Ctrl+Shift+S` invokes package Save As while the Packages surface has focus;
document editors keep their own Save As behavior.

## Opening limits

Archive and folder opening uses the same limits in the GUI and CLI: 250,000
records including skipped entries and implied folders, 128 path components,
64 MiB of index metadata and 64 MiB of source chunk fingerprints. Metadata counts
encoded directory records plus decoded path and diagnostic text; folder source
identity paths also count. These are logical admission budgets, not exact process
memory quotas. Folder fingerprints share one budget across all files, rounding
each file to 64 KiB chunks at 32 bytes per chunk.

An over-limit source is refused with a diagnostic and no partial package listing.
Open a smaller archive or a narrower folder. Source fingerprint limits are checked
before hashing that source; folder admission also checks the remaining aggregate
budget before each file. Opening reports source verification, directory indexing
and index preparation, with cancellation through the existing worker dialog.
ZIP/PK3 central directories are read one record at a time. Opening checks the
classic/ZIP64 entry counts, disk fields, directory boundaries and ZIP64 end
record lengths. Multi-disk archives are refused. Unknown ZIP64 end extensions
are bounded by the same metadata limit; trailing central records or unrecognized
bytes after the directory are refused.

ZIP names use strict UTF-8 when the archive marks them as UTF-8, a valid Unicode
Path extra field when its checksum matches, or the historical CP437 encoding.
Unknown Unicode Path versions and stale checksums fall back to CP437. Malformed
UTF-8, duplicate naming/ZIP64 fields, truncated extra fields and unsafe decoded
paths produce saving-blocking diagnostics. There is no code-page override for
archives produced with an undocumented regional encoding.

Local filenames, flags, compression, CRC and sizes are checked against the
central record, including both local ZIP64 sizes. Streaming entries require a
matching 32-bit or ZIP64 data descriptor, with or without its optional signature.
Damaged local entries remain listed with their reason and source occurrence;
reads, extraction and saves cannot use them. The planned view retains their
exact occurrence. Explicit replacement or deletion can repair the current plan;
Undo and saved drafts retain unavailable original metadata and block export if
it becomes current again. No empty payload is substituted. Directory-header damage also blocks
saving. The optional central-directory digital-signature record is recognized
structurally; validation does not authenticate signatures. Saved ZIP/PK3 names
use UTF-8, so CP437 and Unicode Path names keep their decoded identity across
staging, extraction, asset lookup and reopening.

Combined package sessions share these same budgets across at most 64 layers.
Overridden and skipped source records still count, as do layer labels, relocated
paths and the folders implied by a mount prefix. Combined paths must fit the
depth limit and the reader's 4,096-character path limit. A failed or cancelled
mount keeps the previous session intact;
unmounting releases that layer's charges. This is a core session capability, not
an additional GUI mount control.

The multi-folder lookup used by `map textures` uses this admission policy. If a
folder cannot be indexed or the root count exceeds 64, the lookup refuses its
combined catalog rather than silently falling back to older assets. A missing
requested folder still allows diagnostic results from available folders, but
marks the audit incomplete. JSON exposes `textures.sourceIndexComplete`; false
returns exit 4 even when the map has no external texture references.

These fixed defaults require no setup and cannot be raised through preferences
or CLI flags. The core API permits stricter values. Payload reads, working
imports, saved drafts and temporary copies retain their own budgets.

## Export and reopening limits

Save, Save As, subset exports and compiler package publication use the opening
limits above. Before reading sources or reserving an output file, the writer
checks physical records, implied folders, path depth, encoded directory records
and decoded path/duplicate-warning text. ZIP64 fields are charged when compression
measurement establishes their sizes and offsets. ZIP/PK3 directory growth stays
within that same metadata allowance. Output bytes also have to fit the source
fingerprint budget: the default permits at most 128 GiB of archive bytes, including
headers and directories. Individual formats can impose smaller size/name limits.

`--dry-run` applies the same checks without output, lock, journal or temporary
payload files. A refused write leaves the destination, backup, manifest and
document history intact. Reduce the output or undo the responsible edit, then
retry. The save dialog reports **Checking package output limits…** with record
progress and cancellation before byte-oriented writing phases. Core callers can
lower `PackageWriteRequest::indexLimits`; GUI/CLI defaults cannot be raised.

ZIP folder slashes remain in the archive bytes but are removed from indexed
folder identities. Explicit and implied folders therefore share one identity,
and reopened folders can enter document snapshots without duplicating rows.
The writer also refuses path encodings that cannot round-trip without changing
the name. These are disk-index limits; reader-snapshot and document/history
budgets remain separate, and do not measure total process memory.

## Retained document content

Each package document admits at most 256 MiB of generated inline content and
128 MiB of payload chunk fingerprints. The same limits apply to GUI and CLI
staging, base adoption and draft loading. They cover the base archive, staged
operations, undo, redo and an open edit group, including content hidden by later
edits. Shared byte allocations count once within a document. Deleting a visible
entry does not release content still reachable through the base, operations or
history. Individual generated files retain their 64 MiB limit.

An edit that cannot fit is refused before its new source is hashed or copied.
The current document, revision and redo remain intact. A successful new branch
may reuse space from discarded redo; an open group retains redo until commit so
Cancel can restore it. Generated byte inputs are copied into owned storage,
including inputs backed by a caller's temporary memory.

Saving a draft converts inline content into independently verified disk objects.
Equal content shares one object and one fingerprint allocation. Draft loading
checks the remaining fingerprint allowance before hashing each new object. If
conversion cannot fit, the committed manifest and pending edits remain intact;
previously published unreferenced objects follow the existing draft storage
review/compaction workflow. The 32 MiB draft-manifest limit separately bounds
its own verification hashes. Borrowed filesystem adapters capture their base at
adoption and charge the actual retained fingerprints under the document limit.

`package manifest` exposes exact counters and limits in
`summary.retainedContent`, as decimal byte strings. These fixed defaults need no
setup and have no preference or CLI override; core callers may lower them.
The counters are logical retained-payload budgets, not total process memory.
Independent document/worker snapshots and temporary conversion allocations can
coexist. Retained metadata and reader projections have the separate policies
below. Plan construction and directory replay have separate admission limits;
aggregate independent snapshots still require further bounds and scale work.

## Retained document metadata

Each staged document admits at most 1,000,000 logical records and 128 MiB of
index/text metadata. These limits cover the retained base index and entries,
source and protected paths, WAD source records, conflicts, content-identity paths,
staged operations and undo/redo deltas and labels. An open edit group also counts.
Each unique retained operation reserves its active slot even while hidden in
history, so Undo and Redo work at the limit. History retains at most 256 steps;
groups may nest at most 256 levels.

Record charges bound retained objects and references; byte charges include
admitted base-index metadata and UTF-16 text. They are logical accounting, not
heap or process-memory measurements. Shared operation text counts once per
operation ID, while each history delta counts separately. Imported identities
count per logical record. Filesystem adapters retain the captured native index;
its actual record/text usage is charged at adoption. Generated operations and
group labels own their accepted text,
including inputs backed by a caller's temporary memory.

Edits, unstage actions and group creation check available capacity before changing
the document. Known source metadata is checked before hashing or copying; actual
captured paths and errors are checked again before adoption. Refusal preserves
the document, revision and redo. A successful branch can reclaim discarded redo
or evicted history; an open group retains redo until commit so Cancel can restore
it. Selected GUI unstage actions apply together only after the entire group fits.

Draft save predicts destination object/manifest path charges before payload reads
or directory creation, then checks the actual converted document before commit.
Draft load admits base, operation and history metadata before hashing payload
objects and refuses unreachable operation records. Failed adoption preserves the
open document. Saving an ordinary package and reopening it releases edit history;
saving a draft preserves that history.

`package manifest` reports `summary.retainedMetadata` with decimal-string
`records`, `metadataBytes`, `maximumRecords` and `maximumMetadataBytes` fields.
Defaults require no setup and have no preference or CLI override; core callers
may lower them. Plan construction and reader projections have the additional
limits below. Aggregate independent worker/document copies still need further
admission and performance acceptance.

## Plan preparation limits

Each replay admits 250,000 live entries and conflicts, 500,000 path-index keys,
and 128 MiB of text per materialized representation. Entry keys and distinct
parent keys both count, including an explicit folder that also serves as a
parent. Live entries and conflict diagnostics share one text budget; the path
index has another. Text counts UTF-16 bytes across all staged-entry string fields.
Folder identities admit a conservative serialized-text bound before JSON encoding.
Record limits also bound temporary slot, copy and sort buffers; deleted slots
are reclaimed without changing WAD order. These are logical admission limits,
not an exact heap or process-memory quota.

Individual edits check the candidate's plan and browser view before accepting
the edit. Refusal preserves the revision, operation IDs and redo branch. Edit
groups validate their complete result once at the outer commit; refusal or
cancellation rolls back the whole group. This keeps bulk imports from replaying
the whole plan after each file. Cancelled group IDs remain consumed, as with
explicit group cancellation. Legacy draft history may still describe an
unavailable plan or browser view. Failed preparation exposes a blocking diagnostic
without partial rows and caches the refusal until an edit or Undo/Redo invalidates it.
Cancellation does not poison a retry. Saved drafts retain history for recovery;
Undo or unstage the offending edits. New base adoption refuses excess plan
metadata before payload reads and preserves the current document.

`package manifest` reports decimal-string `maximumRecords`, `maximumIndexKeys`
and `maximumMetadataBytes` in `summary.planLimits`. Core callers may lower the
fixed defaults; there is no preference or CLI override. The policy is preserved
when loading a draft or selecting a subset. It adds no persisted draft field.
Remaining synchronous GUI preparation, WAD/helper allocation audits and
aggregate worker/process memory remain release requirements.

## Summary totals and composition

The Overview composition chart scales its bar to the current text size and
reserves the height needed for legend rows at the inspector width. Percentages
appear inside a slice only when the complete label fits, on a solid theme
background that keeps the text clear over colored hatching. The legend, full
summary tooltip, accessible description and adjacent composition list retain
the category values. Long legend labels may elide; their complete text remains
in the summary. Theme, scale and panel-width changes keep the same category
identities and update the chart layout.

Archive and mounted-session summaries are prepared with their metadata index.
Staging prepares file/folder counts, operation/conflict counts, before/after byte
totals and composition buckets with the derived plan. Repeated status, command
enablement and composition queries reuse these snapshots. Changes, Undo/Redo,
draft loading and mounted-layer changes invalidate the corresponding caches.
Opening and reopening workers prepare staging summaries before UI adoption;
legacy blocked drafts remain available for recovery. The opening dialog reports
summary preparation as metadata records and retains cancellation. Summary and
composition preparation is bounded by the existing plan record/key/text policy,
including bucket indexes, labels and retained blocker messages. These are
per-representation logical limits, not an aggregate process-memory quota.

Byte totals exclude directories. A total above `18446744073709551615` (`2^64 - 1`)
is explicitly oversized; it never wraps to zero. Exactly that maximum remains a
representable metadata total, although individual archive/output limits still
apply. Overflowing source metadata remains inspectable; an overflowing staged
output blocks export. Removing excess entries can restore a saveable plan.
The browser retains entries and exact source identities even when the total or
a composition category is oversized. The folder root, composition overview and
entry details explain the size warning; misleading proportions are omitted.
Individual sizes above Qt's signed formatting range use exact localized byte
counts in row labels, tooltips and accessible text. Select an offending entry
and use **Stage Delete**, then **Save As** to export a repaired package. The
Save As arrow menu offers **Include Staging Manifest**, enabled by default for
the current studio window. A staging manifest hashes all original and final
payloads, including deleted entries. Clear this option when an original damaged
payload cannot be hashed; the archive still verifies every retained payload.
After opening the repaired output, a manifest can be generated from that healthy
source. Damaged original payloads can also prevent draft/recovery checkpoints,
which preserve the original entries and Undo history; the recovery status reports
that failure. Archive-only export still preserves the source file. Undo and Redo
restore the corresponding warning/export state. The CLI offers the same
recovery through `package list` and `package save-as --delete`.
The staging panel also names oversized totals and omits proportional bars.
Metadata inspection does not establish payload integrity; validation and export
retain their format, payload and output limits.
Failed plan preparation reports unavailable sizes/composition, preserves history
and publishes no partial statistics. Cancelling preparation remains retryable.

`package info --json` exposes `package.summary.totalSizeOverflow` and
`totalSizeBytesExact`. The exact field is a decimal string for representable
totals; on overflow both it and the legacy numeric `totalSizeBytes` are `null`.
`package manifest` uses `summary.totalsAvailable`, `beforeSizeOverflow`,
`afterSizeOverflow`, `beforeBytesExact` and `afterBytesExact`. Composition buckets
have `sizeOverflow` and `sizeBytesExact`. The corresponding legacy numeric
fields become `null` on overflow; otherwise they remain JSON numbers for
compatibility. Use the decimal strings when exact large totals matter. These
fields cover totals/buckets; individual-entry numeric fields are unchanged.
Manifest generation still requires successful plan preparation and payload
hashing; a refused preparation returns its existing error rather than a partial
manifest. The GUI manifest choice shares the existing CLI `--write-manifest`
behavior; it is not a persistent preference. No new CLI flag, draft field or
dependency is required.

## Staging list and change details

The Staging tab exposes every operation and conflict through a native Qt list.
Operation and diagnostic rows use two compact lines; select a row to read and
copy its complete paths, source occurrence, generated-content size and conflict
policy in the resizable **Staged change details** pane. Full text is also
available through accessible row metadata and tooltips. Overview and before/after
composition rows retain wrapped text and explicit unavailable/overflow states.

Select All includes every operation, including rows outside the viewport.
Delete/Backspace or the **Unstage** context action removes the selected operation
IDs as one staged group. Overview and diagnostic rows never become unstage IDs.
Enter and **Show Entry** retain exact source occurrences and rename targets.
An unchanged refresh preserves selection; a new snapshot clears obsolete
selection and details. Closing releases the displayed snapshot.

The view shares prepared operation/conflict vectors instead of allocating a
widget item and formatted text for each record. Qt lays out fixed-height change
rows in batches and formats visible rows on demand. Complete layout still visits
the row metadata; this is not a constant-time scrolling or whole-shell latency
guarantee. The CLI, document history, payloads and save/extraction services are
unchanged. No setup or dependency is added.

## Edit history counter limits

Operation IDs and revision numbers are persisted as decimal strings. Their last
usable serial is `18446744073709551614` (`2^64 - 2`); the remaining unsigned
64-bit value stays invalid in draft metadata. New edits check both counters
before changing history or reading a new source. Unstage needs only a revision.
A refused edit leaves the plan, revision and redo intact.

An edit group uses one revision when committed, including nested groups. Empty
or cancelled groups consume no revision; cancelled operation IDs are never
reused. At the counter limit, Undo/Redo, saving the existing draft and archive
export remain available. Export and reopen an ordinary package to start fresh
history; saving and reopening a draft preserves its counters. These safeguards
are shared by GUI/CLI editing and require no setting.

## Reader snapshot limits

Staged readers and adapted package listings admit at most 250,000 records,
64 MiB of logical metadata text and 128 path components. Every file, explicit
directory and diagnostic occupies a record; missing parent folders count too,
including in a reader that exposes only physical entries. Source labels, paths,
type/storage hints, layer labels, notes and warning text share the byte allowance.
Limits are fixed in the GUI and CLI; core callers may lower them.

Admission preserves exact entry indexes and repeated-name positions. It checks
paths without sorting or silently dropping entries. Metadata preparation and
parent-folder expansion support progress and cancellation. Rejected adaptation
keeps the previous reader usable and does not read payloads. Accepted adapter
text owns its storage. Known archive adapters freeze their backing archive and
flatten nested wrappers, so later changes to the original reader object do not
alter the snapshot; disk changes still use the existing source verification.
Other custom readers must provide immutable content backing.

Editable staging retains the owner supplied through `PackageArchive::loadSnapshot`,
including its byte provider and enumerable protected-input roots. Preview, export,
verification, selected subsets and draft checkpointing use that owner; a display
path cannot silently replace it. Subset selectors retain the supplied metadata
index independently of the captured native order. Snapshot verification rejects
short or oversized entry streams and
latches cancellation through callbacks and provider return. PAK/WAD name, size and
directory-offset checks precede source streaming. Known unreadable rows
remain explicit metadata and are skipped by source verification.

An unowned reader describes a filesystem base. Staging captures that base during
adoption, under the remaining document index/hash limits, and binds each supplied
row to a unique physical entry. Explicit ordinals, names, sizes and any supplied
location, CRC or WAD type must agree. Ambiguous or missing entries remain unavailable;
creating a file later cannot supply their content. Replacement/deletion can repair
them, and Undo restores the blocker. No deferred path reopen is used. Use an owned
snapshot for virtual content. An arbitrary provider's allocation policy and
immutability remain its responsibility. Readers declare protected inputs through
`visitProtectedInputPaths`; the shared, non-overridable predicate fails closed if
that enumeration cannot complete. Immutable provider metadata must include these
roots. Staging captures them before payload reads, and rebasing, drafts and recovery
retain them with source-file identities and undo/redo input paths.

Draft metadata version 4 requires a `protectedInputs` array. It retains normalized
absolute roots and resolved aliases, including source directories that have
disappeared. Files and descendants remain protected after reopening. New drafts
cannot enclose a protected input; archive export checks the save lock as well as
the output, manifest and backup. A source-overwrite request still requires the
existing explicit permission and verified publication workflow.

Extraction and archive export capture these immutable roots once per operation.
Output checks use a hash index of complete path components, so matching work
follows output depth rather than rescanning every protected root for every file.
Output aliases are resolved afresh, including Windows junctions and missing
suffixes; extraction still checks output containment and links before creation
and publication. Cancellation is latched during collection, ancestor matching
and alias traversal. No output is created when preparation is cancelled.
An individual blocking filesystem call cannot be interrupted by these checkpoints;
the existing source-identity and publication checks remain necessary.

Protection collection is cancellable and bounded to 250,000 unique roots, 64 MiB
of UTF-16 text and 32,768 characters per path. Retained roots also consume the
document record/text allowances and serialized draft record/JSON allowances.
Invalid, incomplete or excessive declarations preserve the previous document.
The current draft directory is protected implicitly, so saving an unchanged
draft does not add another root. Save As retains the former backing directory.
Foreign-platform absolute roots remain literal provenance rather than becoming
paths relative to the new machine. Versions 1–3 remain readable; their next save
retains known inputs in version 4, but cannot recover roots that older writers
never recorded. Older readers reject version 4 rather than dropping protections.

Virtual WAD providers identify PWAD/IWAD/WAD2/WAD3 through `wadMagic()` and expose
consistent physical ordinals and WAD2/WAD3 directory types through `PackageEntry`.
Missing or inconsistent layout metadata refuses editable adoption before payload
reads. Exact type zero is preserved through native replacement/export and drafts;
new generic texture-WAD additions receive the subtype default. Virtual locations
with no disk offset use zero in draft directory metadata; byte reads remain bound
to the provider. Draft checkpointing materializes those bytes as verified objects.

Known backing archives must also fit their index/fingerprint policies. Snapshot
usage reports the larger backing/projection charges for each counter, preserving
hidden-record and hash admission without repeatedly charging wrapper copies.
These are per-index logical budgets. Reader-owned payloads retain their content
and storage policies, and independent snapshots can coexist.

When a staged view exceeds a limit, Packages shows **Package view unavailable**
with its reason and preserves document history. Headers, composition and the
Textures, Models and Audio views share that refusal; a previous composition
chart is cleared. Available headers count the planned entries. Undo can restore
a usable view;
Redo can return to the same diagnosed state. The CLI returns an error without a
partial listing; `package draft-undo` can recover a saved draft's view while
retaining redo. Validation, comparison, extraction and temporary-copy services
carry the same admission error. Draft base views are checked before publication,
and rejected opening preserves the current package.

New edits and base adoption check the browser projection, including warnings,
unreadable base rows and implied folders. Grouped file imports perform this check
on their existing worker. A refused or cancelled final view returns no accepted
files and preserves the original document. Cancel or Close dispatched after the
worker finishes but before the result is adopted also preserves payloads, revision
and redo history. Individual source-file failures can
still yield an accepted subset when that subset fits. Unstaging a change also
checks the resulting view because removing a deletion may restore many entries.
Ordinary semantic conflicts remain inspectable. Undo/Redo and loading legacy
draft history remain available even when that history exceeds a derived limit.

Folder creation, renaming, deletion, unstage and Undo/Redo prepare their edits
and browser snapshots on a worker. The progress dialog reports records checked
and provides Cancel. The current document, preview ownership and history remain
unchanged until preparation finishes and the shell confirms the same document
revision is still current. Cancelling before adoption discards the whole edit,
including a newly prepared snapshot. Undo/Redo may revisit an unavailable legacy
view and retain its diagnostic and recovery history. Audio reuses the same
prepared browser snapshot. Loading/import handoffs, staging summaries/rows and
repeated small-commit cost still need performance work; this
worker path does not establish an overall UI latency bound.

`package manifest` exposes `summary.viewLimits`: decimal-string `maximumEntries`
and `maximumMetadataBytes`, plus numeric `maximumPathDepth`. Core callers can
lower the fixed policy, retained across base/subset/draft adoption; readers can
apply a stricter policy. The policy adds no persisted draft field or preference.
View admission checks metadata; file import may already have captured an
independent payload before the final check. Each atomic commit currently checks
the complete plan and view. Bulk callers should use operation groups; repeated
small commits on a large document can be costly. That cost, remaining synchronous
GUI preparation and aggregate process-memory acceptance remain work in the
release audit.

## Browsing and filtering

The entry list uses a Qt item model: every matching row remains available, while
labels, icons and accessible text are prepared when the view requests them.
Folder listings sort directories first; a text or property query searches the
whole planned package. Exact snapshot indexes and source-entry labels preserve
repeated WAD names, including when filtering, revealing staged changes or
preparing drag copies. **Unreadable** entries retain a text status and diagnostic.

Index preparation and filtering run on one background worker with one replaceable
pending request. Typing or navigating again cancels obsolete work. Record progress
appears in the list, **Cancel** stops listing, and **Retry** prepares the same
folder/query again. Pending, failed and cancelled lists clear previews and entry
actions; no partial result is adopted. Enter in the filter selects all matches
after the current request finishes. Results are not truncated to visible rows.

The immutable browser index is reused across folder/query changes until the
planned revision changes. It reads metadata without reading payloads and admits
at most 250,000 entries and 250,000 non-root folders. Working parent/occurrence
keys and retained folder-path text share a 128 MiB limit. These are logical
admission limits, not an aggregate process-memory guarantee. The same worker
prepares sorted explicit/implied folder relationships and composition counts/bytes.
The native tree requests labels and accessible descriptions on demand; folder
lookup does not scan the package. Horizontal scrolling keeps deep paths readable;
column width uses visited captions and depth, without measuring every folder.
Composition, tree headers and entry details reuse the cached categories and
summary counts. Query changes retain the current tree selection and scroll
position; a new revision clears stale folder identities while metadata is prepared.

Folder Rename/Delete use the selected folder and document revision, so they also
work while its entry list is filtering. An edit that removes the current folder
returns navigation to the root. Folder navigation does not rebuild the staging
list. Staging rows, before/after composition and remaining load/import projection
handoffs still need broad scale and responsiveness acceptance. The
CLI retains its shared query semantics and unchanged commands; listing controls
require no preference or first-run step.

## Entry previews

The shared details header adapts to the pane width and text scale. Copy and
collapse controls can move below the title and wrap translated captions.
Long source paths use middle elision, with the full path in the tooltip and
accessible description. Resizing preserves the selected section and its content.
Unchanged section rows stay in place during context refreshes and section
navigation. Selecting additional entries keeps the current preview and its text
selection; a completed background preview keeps the chosen Details section.
Changing the current occurrence, including between repeated WAD names, prepares
its own preview.
Related model/audio metadata panes keep headings readable and scroll horizontally
when needed; adjusting the property column remains available.

Package entry selection prepares previews in the background from an immutable
planned snapshot. The inspector shows loading/read progress and **Cancel Preview**;
after cancellation, **Retry Preview** rereads the current selection. New selections
replace pending work and clear old text. Exact entry indexes keep repeated WAD
names separate, and edits/undo invalidate prior results. Generic text/model/binary
samples default to 64 KiB; image/audio samples allow up to 64 MiB. Full samples
must pass the reader's final size/checksum checks. A truncated sample does not
verify its unread tail; use **Validate** to check complete package integrity.
Details shows a bounded excerpt of text so a long unbroken line cannot dominate
the wrapped inspector. The Preview tab retains the full sampled text.
Declared entry sizes retain the full unsigned 64-bit range. Once an entry is
resolved, read failures and cancellation retain that known total while discarded
samples report zero bytes. Missing/ambiguous entries have no known total.
Sizes above 2^53 bytes are displayed as exact decimal bytes; the GUI uses locale
number grouping. This describes archive metadata, not support for reading or
allocating a payload of that size. Sampling and integrity limits still apply.
`package preview --json` adds `bytesReadExact` and `totalBytesExact` decimal
strings plus `totalBytesKnown`; an unknown total has a null `totalBytesExact`.
The existing numeric fields remain for compatibility and may round large
integers. Use the exact strings for byte comparisons. Asset analysis retains the
unsigned total so sampled audio/model metadata cannot appear complete because
of a signed conversion. MP3 duration/frame estimates use checked arithmetic;
unrepresentable estimates remain unknown.

Ogg metadata walks complete pages in sequence using their segment lengths.
Markers inside packet data cannot impersonate final pages. Invalid page order,
continuation, stream identity, trailing data, and unrepresentable sample positions
leave duration unknown. A partial preview reports only the last complete page's
stream-position lower bound. Complete, consistent single-stream headers can
provide a **duration estimate**; codec trimming and nonzero initial offsets may
change playable length. This metadata pass does not verify Ogg page checksums or
decode packets. The Audio editor's full import validates supported Vorbis sounds;
Opus remains metadata/backend playback, without native sample import.

Preview JSON also includes `audioCodec`, `audioChannels`, `audioSampleRate`,
`audioBitsPerSample`, `audioDurationMs`, `audioDurationMsExact`, and
`audioPlaybackCandidate`. Zero duration means unavailable/unknown or sub-millisecond;
the exact string preserves the integer representation, not timing accuracy.
For Ogg, positive duration is the header estimate described above. A playback
candidate is a recognized header, not proof of successful decoding or device support.
Codec analysis is bounded by the sample size and checks cancellation between
phases. The separate Models authoring browser and native drag gestures still
need their own responsiveness acceptance.

## Temporary copies and drag-out

Dragging package rows or opening a script/map copy prepares the current planned
entries on a worker. The copy dialog reports byte progress and offers Cancel;
closing it requests cancellation and waits for the worker. Failure details stay
visible until Close. Selection uses exact entry indexes, so one repeated WAD
name copies the selected occurrence. Path-only script/map requests from Quick
Open or workspace search refuse ambiguous names even if Packages has a selected
occurrence. Stale explicit indexes are refused. Folder copies preserve empty
folders and relative paths; overlapping selections are copied once.

Each batch has a fresh temporary directory. Every selected file must pass the
shared extraction checks before any path is handed to another surface or drag
target. Cancellation and failed integrity checks discard the whole temporary
batch, including files already copied. The batch and its reservations remain
private until the dialog accepts the result. A prior Cancel or Close then shows
**Discarding prepared package copies…** and waits for cleanup; verified removal
releases the reservations. Cleanup failures retain their charge and diagnostics.
An accepted batch shows **Finishing prepared package copies…** while its
reservation is committed. Cancel is disabled during finalization and Close waits
for the result. Existing open copies remain unchanged.
The studio retains successful copies for the session. Code opens them read-only.
Code Save As creates an independent editable file and refuses destinations inside
this window's temporary-copy storage, including directory aliases. Refusal
preserves the current text, save identity and undo state.
Maps remain editable, but Save opens Save As and suggests the active project,
then the package's directory, then the Documents/home folder. The map save
service refuses destinations inside this window's temporary-copy directory,
including paths through directory aliases. Cancellation or refusal preserves
edits and undo history. A successful save adopts the independent file; the
original package and temporary copy stay unchanged. Stage the saved map or its
compiled output explicitly when it is ready for the package.

Temporary batches allow 2,000 files, 10,000 entries including directories, and
512 MiB of declared payload. Entry counts include parent folders implied by
selected file paths. Limits are checked before payload reads. For larger
selections or colliding output names, use **Extract Selected** and its output-path
review. A multi-selection with repeated output names is refused without choosing
an arbitrary occurrence. CLI `package extract --index` and `--as` use the same
streamed integrity/path checks for explicit extraction. Native desktop drag
acceptance and larger shutdown-cleanup evidence remain release gates.

**File > Temporary Package Copies** shows this window's initial payload
reservations, file/entry counts, pending batches and cleanup failures. Defaults
are 2,048 MiB, 8,000 files, 40,000 entries (including folders) and 64 batches.
Each copy atomically reserves all four resources before payload reads or batch
creation; concurrent workers share the same budget. Apply changes the limits
for later batches. Lowering a limit preserves existing copies and can prevent
further copies until the limit is raised. Use Extract Selected for output you
manage yourself. Limits apply across package changes within the same window.

Cancellation/failure releases a reservation only after cleanup succeeds. A
cleanup failure reports the retained path, exposes no handoff paths and keeps
the full reservation charged. Successful batches remain charged until the
studio window closes, even after closing a document, because a drag target may
still use them. This is a logical reservation budget for initial content, not
an on-disk usage scan: later consumer edits and filesystem overhead are not
measured by this per-window reservation budget. Managed copies also reserve
against the shared store limits below. Retained-copy review reports actual
logical payload size; native drag and broader shutdown acceptance remain open.

`package copy-limits --json` inspects the stored policy without creating settings
or temporary storage. Supply `--max-mib`, `--max-files`, `--max-entries` and/or
`--max-batches` to propose changes; only `--write` saves them. `--dry-run` and
`--write` are mutually exclusive. Valid ranges are 1–131,072 MiB, 1–100,000 files,
1–250,000 entries and 1–1,024 batches. Unspecified limits are preserved.

```text
vibestudio --cli package copy-limits --max-mib 4096 --max-batches 128 --json
vibestudio --cli package copy-limits --max-mib 4096 --max-batches 128 --write --json
```

JSON schema 1 reports `scope: "studio-window"`, proposed `limits`, `storedLimits`,
`dryRun`, `updated` and `usageAvailable: false`. Live usage belongs to its owning
GUI window; the CLI does not invent usage for another process. Exit codes are
0 for a successful inspection/proposal/write, 1 for unavailable or read-only
settings, and 2 for invalid, unknown, conflicting or repeated options. Read-only
inspection and proposals do not migrate older settings files.

### Shared copy storage limits

**Review Retained Copies > Shared Storage Limits…** controls initial reservations
across all cooperating studio windows and processes using the same managed store.
Defaults are 8,192 MiB, 32,000 files, 160,000 entries including implied folders,
and 256 batches. Both window and shared limits must admit a copy before any
payload is created. Settings-file overrides do not separate the shared budget:
the policy belongs to the physical temporary store.

Pending work, completed copies, failed cleanup and interrupted processes remain
charged. Verified batch cleanup releases a failed or cancelled reservation;
normal session cleanup or reviewed orphan discard releases the session's retained
charges. Lowering limits preserves existing copies and can block further copying.
Reservation records have checksums; older, missing or invalid records block new
admission until their owners close or the unused sessions are reviewed and
discarded. Their safe, recognized contents remain available for inspection.

`package copy-store-limits [--directory <store>]` inspects the shared policy and
reservations. `--max-mib`, `--max-files`, `--max-entries` and `--max-batches` propose
changes; only `--write` persists them. Valid ranges are 1–131,072 MiB, 1–100,000
files, 1–248,832 entries and 1–1,024 batches. Unspecified fields are preserved.
The entry ceiling leaves room for session metadata and batch directories in the
bounded storage review. Inspection and default/explicit `--dry-run` create no
files or preferences. Writes use the store's `limits.json`, without migrating
preferences. Future-schema preferences prevent policy writes.

```text
vibestudio --cli package copy-store-limits --json
vibestudio --cli package copy-store-limits --max-mib 16384 --dry-run --json
vibestudio --cli package copy-store-limits --max-mib 16384 --expected-policy-sha256 <hash> --write --json
```

The optional `--expected-policy-sha256` binds a proposal or write to an earlier
policy review. The GUI always uses its reviewed token; a concurrent policy change
requires refresh. Without an explicit token, the CLI reviews and checks the policy
within that invocation. JSON schema 1 reports `scope: "managed-copy-store"`,
proposed `limits`, `storedLimits`, `dryRun`, `updated` and `quota`. The quota
includes `reserved`, `accountedSessions`, `complete`, `configured`, `policyValid`,
`policySha256`, cancellation and errors. Incomplete counts are partial, never a
complete zero-usage result. Inspection uses exit 1 for incomplete accounting;
a valid policy change can still succeed while reporting an older session that
continues to block admission. Invalid/unknown/repeated/conflicting options use
exit 2; stale reviews and write failures use exit 1. Successful operations use 0.

These limits reserve initial logical content. They do not enforce later consumer
growth, free disk space or filesystem overhead; actual-usage review remains a
separate snapshot. A damaged policy is preserved and blocks admission; automated
policy repair is not yet available. Native ownership coordinates participating
studio processes and does not exclude arbitrary external filesystem writers.

### Retained copy sessions

Choose **File > Temporary Package Copies > Review Retained Copies…** to inspect
managed copies across studio windows using the same OS temporary directory.
Each window owns a UUID session under `vibestudio-package-copies`; successful
batches and their readers retain its native directory lease. Normal last-owner
release queues bounded cleanup on a dedicated worker, drained before application
exit. A crash releases native ownership; its files remain available for explicit
review. Older unregistered `vibestudio-copies-*` directories are not adopted or
removed by this workflow.

The review shows each session's actual logical payload bytes, file/batch counts,
creation time, path, ownership availability, errors and storage checksum. Usage
includes later consumer edits at inspection time, but excludes filesystem and
session-metadata overhead. The review also shows shared initial reservations
and limits, pending/interrupted batches and each session's recorded charges.
Actual usage and reserved usage are separate bounded snapshots.
Active or unavailable sessions cannot be discarded. Unused sessions require a
confirmation identifying the selected session and its size. Save any temporary
consumer edits you need before discarding. Refresh, Cancel and Close remain
available as appropriate; closing an active operation waits for cancellation.

```text
vibestudio --cli package copy-sessions --json
vibestudio --cli package copy-discard <id> --expected-storage-sha256 <hash> --json
vibestudio --cli package copy-discard <id> --expected-storage-sha256 <hash> --write --json
```

Both commands accept `--directory <store>`. Inspection and the default/explicit
`--dry-run` create no files and never create or migrate preferences. Both dry
and written discard require native exclusion of live owners and an unchanged
review. Only `--write` removes files. Unknown, repeated, conflicting or malformed
options fail with exit 2; unavailable, changed or incomplete storage uses exit 1;
exit 0 means success. Future-schema preferences prevent written discard.
Human output includes full IDs and checksums. JSON schema 1 keeps `sessions`,
`complete`, `cancelled`, actual usage and per-session diagnostics even when
inspection fails. Each session includes `reviewable`, `discardAvailable` and
`storageSha256`, plus `reservationKnown` and `reserved`. The inventory also
includes `quota`; storage `complete` and quota `complete` describe separate
reviews. Discard returns `dryRun` and `discarded`.

A review binds the session path, directory metadata, file names/sizes/times and
record bytes. It does not hash payload contents. Both entry and ownership checks
repeat before deletion. Links, junctions, unsupported entries and unknown root
names prevent cleanup; deletion removes individual reviewed files and empty
directories, never recursively follows a tree. Missing or invalid session
records remain explicitly labelled and can be discarded only when their layout
is reviewable. Cancellation or a locked/changed file may leave partial cleanup;
refresh before a further attempt. The session record is removed after payloads.

Inspection admits at most 128 sessions, 250,000 aggregate entries, depth 128,
32 MiB of relative path text per session and 64 KiB per metadata file. New
session creation refuses a full or unrecognized store. Version-2 session records
retain shared reservations. A native handle on the store's `.coordination`
directory serializes admission, policy changes and cleanup; process exit releases
that handle without a stale lock file. Policy commits and session records use
atomic file replacement. Interrupted metadata fragments remain bounded and
preserved for review; automated policy-fragment cleanup is not yet available.
Native ownership protects participating VibeStudio readers. It does not exclude
arbitrary external writers or establish payload integrity from metadata alone.

## New packages and folders

**New Package** starts an untitled PAK, ZIP, PK3, Doom PWAD/IWAD, Quake WAD2,
or Half-Life WAD3 document without a source archive or temporary source folder.
Even an empty new document is unsaved: closing or replacing it offers Save,
Discard, and Cancel. Save a `.vibepackage` draft to preserve history, or use
**Save As** to write a valid archive, including an empty one.

**New Folder**, **Rename**, and **Delete** work on the planned directory tree.
Folder context menus and F2/Delete in the folder tree expose the same actions.
A folder rename or deletion is one undo step covering all descendants, including
empty folders. Selecting both a folder and its children deletes that subtree
once. Rename requires an unused destination; it never merges or replaces another
folder. Moving into itself or an ancestor, unsafe paths, and file/folder
collisions are rejected before any entries move. Case-only renames are supported.
Replaying an edit checks its captured subtree identity; removing an earlier edit
can block the entire dependent folder edit until it is unstaged and selected again.

WAD packages have a flat lump namespace, so folder actions are disabled.
Opening a disk folder also retains its empty subfolders, and added/removed
subfolders invalidate the captured source tree. ZIP/PK3 preserve explicit empty folders. PAK cannot represent them: export blocks
until they contain a file, are deleted, or the output format is changed to ZIP/PK3.

```sh
vibestudio --cli package create ./new.pk3 --mkdir maps --add-file ./start.bsp --as maps/start.bsp --dry-run --json
vibestudio --cli package create ./work.vibepackage --format pk3 --mkdir textures --json
vibestudio --cli package create ./textures.wad --wad-magic WAD2 --json
vibestudio --cli package draft-save ./work.vibepackage ./renamed.vibepackage --rename-folder textures --folder-to art/textures --json
vibestudio --cli package stage ./renamed.vibepackage --delete-folder art --json
```

`package create <output>` infers archive format from the filename. For a draft,
`--format` chooses its intended archive type and defaults to `pk3`. WAD creation
accepts `--wad-magic PWAD|IWAD|WAD2|WAD3`; the default is `PWAD`. Existing outputs
require `--overwrite`. Archive creation reports the usual `write` JSON result;
draft creation reports `outputPath`, `draftPath`, `written`, `dryRun`, and `staging`.
Exit codes are 0 success, 2 invalid arguments, 1 draft persistence failure,
and 4 blocked archive output.

All staging routes accept repeated `--mkdir`, paired `--rename-folder` /
`--folder-to`, and `--delete-folder`. One invocation is one edit group. The order
is folder creation, file imports, replacements, file renames, folder renames,
file deletions, then folder deletions. Folder targets must be unused regardless
of file conflict policy. Empty or missing option values are errors.

`package create` and `package draft-save --dry-run` verify all draft payloads,
including redo-only inputs, metadata limits and destination constraints. They
create no draft directory, objects, or lock file and leave the document's saved
revision unchanged. A dry run cannot reserve a destination or guarantee a later
write against external filesystem changes.

## Drafts and edit history

Adding or replacing a file retains a verified independent working copy before the
edit is accepted. Later changes to, or removal of, the original file do not change
that import. Grouped undo/redo, background readers, previews, extraction and asset
handoffs keep the same bytes. Original paths and logical modification times remain
provenance; reads use the retained copy. Both paths remain protected from output.

Working imports stream in 64 KiB chunks into managed sessions under Qt's configured
temporary directory and verify the copy before adoption. System temporary aliases
are resolved once; retained paths use the real directory and cleanup refuses links
or junctions. Cancellation or copy failure preserves the previous edit state. Temporary files remain alive while referenced by a document,
history entry or worker snapshot; the last release queues guarded file cleanup on
the worker pool. Dropping a redo branch releases unreachable copies. Draft save
replaces the live backing with durable draft objects without invalidating older
readers. The original files are never hard-linked or modified.

These working copies need writable temporary disk space. Configurable reservations
bound their payload bytes and file count; [Working import storage](#working-import-storage)
provides usage review and explicit cleanup of abandoned sessions. Save a draft or
use recovery checkpoints for restart persistence: working files have no editing
document or history manifest. Opened archive/folder base content retains
source-change checks until it has been preserved in a draft or checkpoint.

**Save Package Draft** (`Ctrl+S` on Packages) preserves the editing document in
a `.vibepackage` directory. **Open Package Draft** resumes its base content,
staged operations, and undo/redo position. Keep the entire directory when moving
or sharing it. `document.json` describes the document; `objects/` contains
independent payload copies addressed by SHA-256. No original installation or
imported file is needed after a successful draft save.

**Undo Package Edit** (`Ctrl+Z`) and **Redo Package Edit** (`Ctrl+Shift+Z`) also
have toolbar and Edit-menu controls. File batches, selected deletes, and selected
unstaging each form one undo step. Changes staged through authoring services use
the same history. Up to 256 edit groups are retained; older operations remain in
the plan. A new edit after undo discards the redo branch. Saving a draft preserves
redo content as well as the current plan, and undoing back to the saved revision
restores the clean state. Closing or replacing a modified document offers Save,
Discard, and Cancel.

Operation progress uses the shared studio theme, with contrasting text over the
filled and empty track. Its height follows the current text scale, including
changes while a worker is running. Record counts and byte counts remain textual
and accessible, alongside the phase summary and Cancel action. Byte quantities
choose B, KiB, MiB or larger binary units: a half-read 128 KiB file shows
`64 / 128 KiB`, not equal rounded MiB counts. Partial quantities round down and
totals round up to a hundredth of the shared unit; completion uses the total's
rounding. A positive amount below one hundredth is shown as `<0.01` of that unit.
Exact localized bytes remain in the progress tooltip and accessible description.
Unknown byte totals have no denominator and remain indeterminate (static with
reduced motion); validation retains its independent file-count progress. Reading
all reported bytes completes that phase, while publication/reload still follow
the operation's phase summary. Finished operations clear old byte details.

Draft save/open runs on a cancellable worker with byte progress. New payloads are
written independently and checked before the metadata commits atomically. An
interrupted save leaves the previous committed document usable; unreferenced
objects may remain. A changed manifest or damaged/missing referenced payload
blocks reopening or saving, and malformed history is rejected before adoption.
Current payloads that fail reading and skipped source records block draft creation.
Known unreadable source metadata (for example, a bad local ZIP header or unsupported
compression) is retained explicitly as unavailable; its bytes are not stored in the
draft. It remains visible, blocks archive export and can be replaced or deleted.
Conflicts caused by staged edits can be saved and repaired after reopening.

If a repair deletes or replaces an original occurrence that cannot be read,
the draft can preserve its metadata and history with an explicit unavailable-content
record. Every current readable payload and every imported/generated undo/redo
payload still has to be copied and verified. A bad stored draft object, changed
source, cancellation, disk/write failure or quota refusal is never converted
into an unavailable-content record. Converting a new payload-read failure into
historical metadata needs a successfully prepared plan establishing that the
original occurrence is no longer current. Source metadata already marked
unreadable, and existing explicit unavailable states, can be checkpointed without
fabricating payload bytes.

Metadata version 3 introduced unavailable base records; each stores a bounded
`unavailable` reason instead of an `object` hash. Current drafts write **version 4**,
which also preserves source protections. Versions 1–3 remain readable. Older
applications reject unsupported versions rather than inventing missing payloads
or discarding protections.
The original path, declared size, ordinal and edit history remain available after
the original package is removed. The browser reports unavailable Undo content.
Undo can reveal that occurrence, but its previews/reads fail and archive export
is blocked until it is replaced or deleted again. Redo restores the repair.
An already explicit unavailable state can itself be checkpointed during Undo.
This preserves the repair; it cannot reconstruct bytes that were unreadable.

Staging manifest rows for these records have `contentAvailable: false`, a null
`sha256` and `unavailableReason`. No digest is invented. Ordinary objects retain
their strict hashes. Metadata and history limits also charge diagnostic text.
Draft paths cannot traverse symbolic links or junctions. Filesystem checks cannot
exclude an unrelated process changing a path during the final check/commit window.

An open draft retains its history across archive exports. Saving a regular
archive without first saving a draft still opens the exported archive and starts
a new staging history. Automatic recovery uses the same document format. Saved
draft limits and reviewed cleanup are described below.

## Saved draft storage

**File > Recover Packages > Saved Draft Storage…** reviews a selected
`.vibepackage` directory, shows its usage and unused files, and controls limits
for future saves. Defaults are 32,768 MiB and 200,000 files per draft; supported
settings ranges are 128–131,072 MiB and 1–250,000 files. GUI saves, CLI draft
creation/saves/undo/redo, recovery restoration and actual texture-to-draft saves
share these preferences. Recovery checkpoints and working imports have separate
store limits. Lowering limits preserves existing content.

Save preflight verifies reachable content and history without creating files.
Logical accounting includes existing payloads, unused objects, metadata and room
for a replacement manifest while the old one remains present. Identical payloads
share an object. An unchanged save verifies the draft without rewriting metadata,
even after its limit is lowered. A changed save requires enough byte and file
headroom for its peak write. Limits are admission checks, not physical free-space
reservations; filesystem overhead is excluded. Preflight adds verification I/O,
so broad performance and disk-full acceptance remain open. A real save can
recover a writer lock left by a crashed process after preflight succeeds; explicit
read-only previews refuse a present writer lock and leave it untouched.

Review verifies every referenced payload and undo/redo history before proposing
cleanup. **Reclaim Reviewed Space…** removes only reviewed unreferenced objects
and recognized interrupted writes. It preserves the manifest and all referenced
objects. Close the draft and wait for its background readers first. A directory
lease follows saved and loaded document snapshots, history and flattened readers;
another process's participating reader also blocks maintenance. The lease creates
no file and is released after a crash. Older snapshots reject a replaced draft
root even when its payload statistics are identical. Recovery checkpoints can
continue within quota while older readers defer optional cleanup; retained unused
bytes still count, and retirement refuses active readers. Windows uses directory-handle sharing;
Linux/macOS use advisory `flock`. Unsupported native exclusion refuses maintenance
while retaining the conservative read/save fallback where available. Native
macOS/Linux and network-filesystem acceptance are still required.

The manager shows the first 100 unused filenames; the CLI provides the full
bounded review. Corrupt or incomplete drafts, foreign files, links, changed review
checksums and scan overflow block compaction. Ordinary draft discard is not
offered. Review and cleanup run on cancellable workers. A partial cancellation or
failure reports how many unused files were removed; refresh before continuing.
Current and redo content remain intact.

```sh
vibestudio --cli package draft-storage ./work.vibepackage --json
vibestudio --cli package draft-compact ./work.vibepackage --expected-storage-sha256 <storage-sha256> --dry-run --json
vibestudio --cli package draft-compact ./work.vibepackage --expected-storage-sha256 <storage-sha256> --write --json
```

`draft-storage` returns `storage` (completeness, errors, retained/reclaimable bytes,
file counts, referenced-object count, unused files and manifest/storage hashes)
and configured `limits`. `draft-compact` defaults to no-write review. Its JSON
reports `dryRun`, `readerExclusion`, `reclaimedBytes`, `reclaimedFiles` and `error`,
including partial failure counts. A dry run creates no locks and leaves reader
exclusion unproven (`readerExclusion: false`); only `--write` obtains exclusion.
Exit codes are 0 success, 2 invalid arguments and 4 review/maintenance failure.
Unknown/repeated options, extra arguments and combined `--write --dry-run` fail.
Preferences are `packages/draftMaximumMiB` and `packages/draftMaximumFiles` in the
selected settings profile.

Storage review bounds are shared with recovery (250,000 files and 32 MiB
metadata). Fingerprints cover membership, file statistics and metadata; cleanup
also fully verifies referenced objects. Native locks coordinate participating
VibeStudio readers, not arbitrary external writers or older clients. Final
check/delete races and same-statistic external changes remain filesystem
boundaries. No draft schema or new runtime library is introduced.

## Working import storage

**File > Recover Packages > Working Import Storage…** shows retained payloads,
reserved space and sessions, and controls the working limits. Defaults are
8,192 MiB and 50,000 files; ranges are 128–131,072 MiB and 1–100,000 files.
These settings also apply to actual CLI imports. Lowering a limit preserves
existing content and blocks later admissions that would exceed it. There is no
automatic eviction. A document, undo/redo entry or background reader keeps its
session lease until its last reference and queued cleanup finish. Saving a draft
can release working copies once earlier readers finish.

The store is `<resolved-temporary-directory>/vibestudio-package-imports/`.
Each UUID session has checksummed `working.json` reservation counters, a `.lease`
and independent `objects/<uuid>.blob` files. A shared store lock serializes
reservations across cooperating processes. Reservations commit before payload
creation, including file slots for empty imports; deletion precedes counter
release. Interrupted operations can leave excess reservations; admission cannot
reuse reserved budget while an app owner still retains it. Invalid metadata blocks new
imports until reviewed maintenance. Byte limits cover logical payloads, including
copies in progress; metadata and filesystem overhead are excluded. Admission reads
bounded aggregate counters instead of scanning every existing payload per import.

Select a session to inspect its complete ID, paths, usage, errors and storage
checksum. **Discard Selected Session…** confirms the reviewed selection, then
checks its lease and current storage before removing recognized files. Live sessions
cannot be discarded. Incomplete sessions can be cleaned up if their layout can
be fully reviewed. Unknown files, links, junctions, changed storage or scan limits
block deletion. Cancellation may leave part of an abandoned session; refresh before
trying again. Inventory and cleanup run on cancellable workers; Close remains
available. No working-file restoration is offered: use drafts or checkpoints.

If storage stays busy after its owner exits, **Review Lock Files…** lists the
store/session locks and their stale-removal guards. Review the path and checksum,
then confirm release. The worker refuses a changed file, a live native lock,
links, nonregular files or metadata above 64 KiB. Empty locks left by an
interrupted creation are reviewable. Releasing a lock keeps every payload;
session discard requires its own review. No automatic age-based release occurs.

Normal GUI/CLI shutdown releases documents and worker readers, then drains the
dedicated import-cleanup queue before destroying Qt. An interrupted process can
still leave a session or lock for explicit review. Cleanup failures retain
storage and emit diagnostics instead of recursively removing it. Once one
cleanup fails, the session retains its remaining queued files and reservations
for review instead of repeating the store-lock timeout for every file.

```sh
vibestudio --cli package working-imports --json
vibestudio --cli package working-unlock .store.lock --expected-lock-sha256 <lock-sha256> --dry-run --json
vibestudio --cli package working-unlock .store.lock --expected-lock-sha256 <lock-sha256> --write --json
vibestudio --cli package working-discard <id> --expected-storage-sha256 <storage-sha256> --dry-run --json
vibestudio --cli package working-discard <id> --expected-storage-sha256 <storage-sha256> --write --json
```

All three commands accept `--directory <store>`. Listing creates no files and returns
`inventory` (sessions, payload/reserved bytes and file counts, lease presence,
reviewability, errors, storage checksums and completeness) plus configured `limits`.
Its separate `locks` array reports `relativePath`, `bytes`, `exists`, `reviewable`,
`lockSha256` and `error`; session usage completeness does not assert that locks
are idle. Lock fingerprints include absolute path, native file identity,
timestamps and contents. Only `.store.lock`, `.store.lock.rmlock`, and canonical
`<uuid>.working/.lease` or `.lease.rmlock` paths are accepted. `working-unlock`
defaults to dry run and reports `dryRun`, `released`, `relativePath`, `lockSha256`
and `ownerExclusionChecked`. Both dry run and write prove native exclusion at
that moment; write repeats the check. A missing lock fails without creating it.
Discard defaults to a no-write review; successful JSON reports `dryRun`, `discarded`
and `leaseChecked`. A dry run creates no locks and reports `leaseChecked: false`:
only `--write` proves that the session is no longer live. Exit codes are 0 success,
2 invalid arguments, and 4 incomplete inventory or operation failure. Unknown or
repeated options and combined `--write --dry-run` are rejected. The preferences
are `packages/importMaximumMiB` and `packages/importMaximumFiles` in the selected
settings profile. Limit inspection uses read-only settings access, including
for legacy profiles: it neither creates preferences nor migrates their schema.

Scans are bounded to 64 sessions, 100,000 payload files in total and 32 top-level
entries per session; metadata reads are capped at 64 KiB. Storage checksums cover
membership, statistics and bounded metadata content, not all payload bytes. These
cooperating locks/counters do not prevent external programs changing files or
forging metadata. Same-statistic changes and the final check/delete race remain
filesystem boundaries. Lock recovery uses exclusive Windows file sharing and
handle-based deletion, or macOS/Linux advisory `flock` plus native identity
checks. Unsupported exclusion refuses release. Noncooperating Unix writers
can bypass advisory locks or race the final path check; remote filesystem
semantics and native macOS/Linux execution remain acceptance gates.
Worst-case performance and disk-full/network/power-loss
acceptance remain release work. Recovery
checkpoint quotas apply to their separate store.

## Automatic recovery

Unsaved packages receive local checkpoints every 30 seconds by default. **File >
Recover Packages** lists copies and controls automatic checkpointing and its
5–600 second interval. Turning it off keeps existing copies. The package browser
shows waiting, saving, saved, disabled, or failure status; failures also appear in
Activity. No cloud service or additional dependency is required.

A checkpoint atomically commits recovery details together with the draft
manifest. It preserves base content, empty directories, staged edits, duplicate
entry identities and all readable reachable undo/redo payloads. A repaired package
can record unavailable original history as described above. Recovery status and
chooser details warn about the count; inventory JSON exposes `unavailableBaseCount`.
Restore verifies every referenced object and retains those explicit limitations.
Saving a checkpoint never
marks the working document saved. One worker and one replaceable pending snapshot
keep rapid edits from starting concurrent copies. Save, successful replacement,
and approved close/discard retire that document's checkpoint; retirement cancels
pending work and cannot resurrect a closed document. A failed or cancelled open
keeps the current document and its recovery copy.

The store is `package-recovery/` under Qt's application-local data directory.
`--settings-file` places it beside that settings file, including isolated tests.
Inventory reads at most 128 recognized UUID directories, 500,000 storage files
(250,000 per copy), 4,096 store-root entries and 64 MiB of metadata (32 MiB per
manifest). Damaged and incomplete records remain visible. **Metadata
checked** does not assert payload validity. Restoring verifies every referenced
object and every history delta on a cancellable worker before saving an independent
new `.vibepackage` directory. Existing outputs, the recovery store, recorded source
inputs and the original draft are protected. The chosen manifest checksum rejects
a stale selection. The original checkpoint remains until explicitly discarded.

An editor holds a session lock for the document lifetime. Restore takes a separate
write lock; discard requires the session lease and selected review checksum.
A store lock serializes checkpoint accounting and cleanup across editor sessions.
Dead process locks use Qt's stale-lock handling. Removal preflights the bounded,
two-level store, refuses links/junctions and unrelated files, and never recursively
follows paths from a manifest. After a successful checkpoint, objects absent from
the current base and complete history are reclaimed; maintenance failures leave
the committed checkpoint readable and are reported separately. A retry first
reclaims this session's objects that are unreachable from its last manifest.

Recovery defaults to **8,192 MiB and 32 copies**. The chooser exposes usage and
limits of 128–131,072 MiB and 1–128 copies. Limits cover logical data-file sizes,
including incomplete files and the peak space for streamed objects and atomic
manifest replacement. Lock files and filesystem allocation overhead are excluded;
this is not a physical free-space reservation or a quota on ordinary drafts.
Identical stored objects can be reused with only manifest headroom. Limits stop
new checkpoints without evicting old copies; the last committed manifest and live
edits remain intact. Lowering a limit never removes existing data. Unknown paths
or a truncated scan prevent claiming complete usage and block another checkpoint.

An incomplete first checkpoint has no committed manifest and cannot be restored.
The chooser can discard it after review. `storageSha256` fingerprints the bounded
file list, sizes, timestamps and bounded manifest content; it does not verify
payload bytes. Added or changed files invalidate the selection. Unknown files,
links and junctions block the entire deletion before any files are removed.
External programs can ignore cooperating locks; statistics cannot detect all
same-size writes with preserved timestamps, and no check eliminates a foreign
write in the final check/delete window. There is no automatic age-based eviction.
Disk-full/power-loss acceptance remains open; ordinary saved-draft maintenance
uses the separate reviewed workflow above.

```sh
vibestudio --cli package recoveries --json
vibestudio --cli package draft-recover <id> --expected-sha256 <manifest-sha256> --output ./recovered.vibepackage --dry-run --json
vibestudio --cli package draft-recover <id> --expected-sha256 <manifest-sha256> --output ./recovered.vibepackage --json
vibestudio --cli package recovery-discard <id> --expected-sha256 <manifest-sha256> --write --json
# The storage review token also supports incomplete copies. Preview first:
vibestudio --cli package recovery-discard <id> --expected-storage-sha256 <storage-sha256> --json
```

All three commands accept `--directory <store>`. `recoveries` returns `inventory`
with metadata validity, timestamps, source/draft provenance, revision/history counts,
manifest/storage review checksums, logical storage and temporary bytes, file counts,
manifest/session-file presence, errors and truncation. `storageComplete` says
whether the aggregate `storageBytes`/`storageFiles` totals are complete; partial
totals are not a safe quota measurement. A top-level `limits` object reports
`maximumBytes` and `maximumCopies` from the selected settings. `draft-recover`
returns `recovered`, `dryRun`, and `draftPath`; discard defaults to a no-write
preview and needs `--write` to commit. Discard accepts exactly one of
`--expected-sha256` (manifest) or `--expected-storage-sha256` (storage review);
restore requires the manifest checksum. Dry runs create no lock or output files and
conservatively refuse existing lock files. Unknown, duplicate, empty and incompatible
options are rejected. Exit codes are 0 success, 2 usage, and 4 validation/operation
failure or incomplete/damaged inventory. `package recover` remains the separate
archive-publication journal command.

The package browser, folder tree, composition, preview, validation, extraction,
selected-file exports and temporary editor copies read the current planned view.
Additions appear immediately; renames move entries and deletions remove them.
Undo/redo refreshes those views, including Textures, Models and Audio. Workspace
search, Quick Open and asset property filters use the same paths and metadata.
A captured worker snapshot keeps its own revision while editing continues. **Review Changes**
compares the base against the plan; **Compare** compares the plan with another
package. Conflicts remain visible in staging and entry diagnostics. Readable
entries remain inspectable while other edits are blocked, but blocked plans
cannot be extracted or rebased for export.

Repeated names have a source-entry label in the browser. Preview, Replace,
Rename and Delete address the selected file occurrence; selected deletes form
one undo group. Staging rows, history labels and Show Entry keep that identity.
A rename retains the original position in WAD output. Path-only edits and
previews refuse ambiguous names. Image previews now decode the selected
occurrence on a background worker using the planned snapshot. Changing rows or
source revisions retires old results; the Preview tab shows loading or a decode
error until pixels are available. **Export Selected** addresses the same exact
occurrences and staged bytes, with required WAD group members shown before saving.
Other preview types and drag copies still need the remaining worker/streaming pass.

```sh
vibestudio --cli package draft-save ./mod.pk3 ./work.vibepackage --add-file ./note.txt --as docs/note.txt --json
vibestudio --cli package draft-info ./work.vibepackage --json
vibestudio --cli package draft-undo ./work.vibepackage --json
vibestudio --cli package draft-redo ./work.vibepackage --json
vibestudio --cli package save-as ./work.vibepackage ./release.pk3 --json
```

`draft-save` accepts the usual add/replace/rename/delete options as one group.
Replacing an existing draft requires `--overwrite`; `draft-undo` and `draft-redo`
explicitly modify that draft and commit the new history position. `draft-info`
verifies all referenced payloads and is read-only. These commands reject unknown,
empty, incompatible, and extra arguments. JSON includes the draft path, revision,
undo/redo availability, operation/file counts, and whether the plan can export.
Exit `0` means the draft operation succeeded, even if staged conflicts still need
resolving; `2` denotes invalid arguments, `1` a load/save failure, and `4` no
available undo/redo step. `package info`, `list`, `preview`, `extract`, `validate`,
`stage`, `manifest`, and `save-as` also accept draft directories. Read commands
inspect the planned content; they never list the draft's internal object store.
Unfiltered `list --json` reports `entryIndex` (position in this reader snapshot)
and `sourceOrdinal` (original directory position, or -1 for new entries without
a source occurrence).
Indexes may change after edits; they are not persistent identifiers. Draft
inspection/export does not implicitly rewrite a draft.

Use `package preview <package> --entry-index N` for the exact row returned by
`list --json`. Edits instead use the persistent zero-based source ordinal:
`--replace-ordinal N --replace-file <file>`, `--rename-ordinal N --to <name>`,
and `--delete-ordinal N`. These options also work with stage, manifest, save-as,
staged comparison and draft-save. Repeat pairs for multiple entries. Choose
one selector kind (path or ordinal) within each replacement or rename group.
An operation records both its ordinal and expected current path; removing an
earlier rename blocks dependent edits instead of redirecting them to another
entry. New entries without a source ordinal use their unique path. Browser
labels count from 1; CLI indexes and ordinals count from 0.

All new drafts use metadata version 4, preserving source protections, occurrence
selectors and unavailable original history through undo/redo. Versions 1–3 remain
readable; older binaries reject unsupported versions rather than ignoring their
semantics. Folder operations were introduced with version 2; binaries without
these operation types reject them explicitly.

Draft metadata is limited to 32 MiB and 250,000 combined base, directory,
conflict, WAD metadata, operation, current-operation, history, change and
protected-input records.
Payload storage streams in 64 KiB chunks. Drafts preserve logical file timestamps
independently of the storage files' timestamps. They add no library dependency.

Level dependency exports resolve Quake III brush and patch material tokens such
as `studio/curve` under `textures/`, including shader scripts and their images.
Existing full material paths remain accepted for lookup. A dependency subset
contains assets; add the compiled BSP separately when preparing a playable PK3.

## Edit WAD groups

**WAD Groups** in Packages and the command palette inspects the current staged
Doom WAD. Choose a map, namespace or local texture-table group, choose the edit,
and use **Review Edit**. The worker verifies the source and lists exact changes
in pages of 500. **Apply Reviewed Edit** adopts one undoable edit; closing or
cancelling leaves the document untouched. Later changes to the document invalidate
its review. Save Draft preserves the grouped operations and their undo/redo history.

Map renames update the map marker and its unambiguous `GL_` companion together;
selecting the GL group also includes the main map. Deletion includes every member
of both runs. UDMF includes sidecars through `ENDMAP`. Deleting a namespace removes
its complete region, including nested regions and staged native textures; deleting
only a nested region keeps its enclosing markers. Local `PNAMES`, `TEXTURE1` and
`TEXTURE2` records form a deletion group. Names inside a flat/patch/sprite namespace
keep their resource meaning even when they match a global table or map lump.

Map labels use 1–8 ASCII letters, digits, underscores or hyphens (five characters
with GL nodes), begin with a letter, digit or underscore, normalize to uppercase,
and must not collide with another entry
or a reserved lump name. Namespace and texture-table labels define their meaning
and cannot be renamed here. Broken namespace boundaries, incomplete maps,
ambiguous companions, unreadable records, changed sources and stale review
fingerprints block the edit atomically. Individual occurrence edits remain
available for deliberate low-level work.

These operations work in new and opened PWAD/IWAD documents and their drafts.
New WADs assemble binary/GL map runs in the planned view, before review. Loose
map records require one unambiguous owning marker; use `MAPnn` or `ExMy` when
adding unordered binary inputs, then rename the complete group if needed. The
assembly preserves UDMF sidecars, namespace regions and explicit native texture
anchors. Ambiguous ownership blocks publication until repaired. Group review,
preview, subset export and saving consume that same order; saving performs no
second ordering pass. Put UDMF sidecars before `ENDMAP`. Conversion
from a non-WAD source retains the existing single-map canonical fallback and
rejects ambiguous multi-map ownership. WAD2/WAD3 use individual texture editing. Map metadata,
scripts, texture/patch references and other game-asset dependencies are not rewritten;
review those dependencies before publishing a renamed or reduced package.

```sh
vibestudio --cli package groups ./maps.wad --json
vibestudio --cli package stage ./maps.wad --rename-group map:11 --group-to MAP03 --groups-fingerprint <fingerprint> --json
vibestudio --cli package draft-save ./maps.wad ./work.vibepackage --delete-group map:11 --groups-fingerprint <fingerprint> --dry-run --json
```

`package groups` returns schema-1 `inventory`: a content/plan fingerprint and
group `id`, `name`, `kind`, `memberCount`, `canRename`, `error`, and compact
inclusive planned-entry `ranges`. Indexes/counts are decimal strings. Source-based
IDs include the zero-based source ordinal; staged groups use their current operation
ID, which can change after editing. Refresh the inventory after an edit and use
returned IDs rather than constructing them. The fingerprint includes source
and draft content identities, revision, entry metadata and generated payloads.

Staging routes accept repeated `--rename-group` paired with `--group-to`, or
`--delete-group`, plus exactly one `--groups-fingerprint` from the inventory.
Groups must not overlap and cannot mix with individual entry/folder or conflict-policy
edits in one invocation. `stage`, `draft-save`, `save-as`, `manifest` and staged
`compare` share the service. Dry runs create no package, draft, import copy or
settings change. Rejected group edits return 2 on staging/write routes; `groups`
returns 2 for malformed arguments, 1 for loading failures and 4 for unsupported
or blocked group inspection. Staged comparison retains its existing validation
exit behavior. Archive publication still performs normal integrity/output checks. CLI comparison
reads draft contents through the planned reader, including both-sided draft
comparison; staged comparison retains the captured draft revision and history.

## Export a selected subset

Use **Packages > Export Selected** to review the selected planned files or folder
contents. Repeated names retain their exact occurrence. The review distinguishes
selected files from required group members and displays source positions and
warnings. Preparation and export run on workers, and closing requests cancellation
before joining the worker. Exports use an independent snapshot, preserving the
live document and its undo history. Output cannot replace the source, staged
inputs or draft content. Replacing a separate existing output needs confirmation.
The review uses pages of up to 500 rows to keep widget work bounded; every entry
is available through the page control. Export includes every reviewed page.

Doom IWAD/PWAD subsets expand binary and UDMF map groups, matching GL node groups,
and required namespace markers. Binary groups require `THINGS`, `LINEDEFS`,
`SIDEDEFS`, `VERTEXES` and `SECTORS`; node/blockmap records can be absent in compiler
inputs, so group preservation is not a launch-readiness check. Selecting a
namespace marker includes that entire region; selecting an ordinary member
includes its enclosing boundaries. Namespace context keeps resources named like
map records (such as a flat named `THINGS`) from being mistaken for map groups. Local
`PNAMES`, `TEXTURE1` and `TEXTURE2` tables stay together. Incomplete maps, unmatched
markers, ambiguous GL companions and skipped/unreadable WAD records block export.
The current WAD plan order is preserved, including source-free new documents,
named UDMF maps, sidecars and native texture anchors.
WAD2/WAD3 subsets preserve exact selected texture records and their types.

This protects container grouping; it does not prove a complete playable game or
follow all texture/patch/game-code dependencies. A texture definition without a
local `PNAMES` emits a base-game-table warning. Cross-format exports still apply
the destination writer's path, name and size constraints. Reviewed group edits
use the same membership rules described above.

```sh
vibestudio --cli package list ./maps.wad --json
vibestudio --cli package subset ./maps.wad ./map-assets.wad --entry-index 17 --dry-run --json
vibestudio --cli package subset ./work.vibepackage ./assets.pk3 --prefix textures --where "ext=png" --json
```

Indexes are zero-based rows from `package list --json` for the same current
snapshot. Repeat `--entry-index`, `--entry` or `--prefix`; those selectors form a
union before `--where` filtering. A query alone searches every file, including
repeated names. Path-only ambiguous selectors fail. The JSON `subset` object has
schema version 1 with each member's `entryIndex`, `sourceOrdinal`, `virtualPath`,
`sizeBytes` (decimal string), `selected` flag and inclusion reason, plus
`totalBytes` and warnings. Dry runs return the same review and write no output or
preferences. Subset exports reject in-place and staging-edit options; save edits
in a `.vibepackage` draft first. The command accepts normal format, compression,
manifest and explicit overwrite options for a separate output.

## Review and save

1. Create a new package or open an existing package, draft or folder in **Packages**.
2. Stage additions, replacements, renames, or deletions. The staging summary
   shows conflicts and blockers; **Unstage** removes an operation.
3. Choose **Review Changes** from the package toolbar or command palette. The
   comparison includes generated content held in memory. Search paths, inspect
   before/after sizes and hashes, and export the report as JSON. By default,
   unchanged verified entries are hidden; unchecked entries remain visible.
4. Choose **Save As**, select the destination format and compression, and follow
   progress in the save dialog. Replacing an existing package requires explicit
   confirmation and retains the previous bytes at `<output>.bak`.
5. For a regular archive, a successful save opens the written archive and resets staging. Further edits
   read the new archive directory and offsets. Failed or cancelled saves retain
   the staged plan for retry. An open draft keeps its independent plan and history.

Opening, file staging, extraction, comparison, validation, and writing run on workers.
Opening and staging fingerprint sources with byte progress and cancellation
within a file. Cancelling a staging batch keeps the previous plan; a failed or
cancelled open keeps the current package and its edits. Archive and staged-plan
comparison stream each file with its source/result label, path and byte progress.
The wrapping status line keeps the active side/file visible above longer
source paths in the details pane.
Comparison and validation can cancel within a file; partial comparison reports
retain only completed rows and their byte totals. Archive saves also cancel
within source reads, compression measurement, compression and manifest hashing.
Plan preparation also reports metadata progress and checks cancellation during
edit replay, parent indexing, folder identity/rewrite work, sorting and WAD
assembly. Cancelling preparation discards its temporary view and preserves the
document, Undo/Redo and any existing export files. Retrying rebuilds the complete
view. Folder identity hashes remain compatible with existing saved drafts.
The dialog shows the phase, file counts, current path and per-file byte progress. Closing a running dialog
requests cancellation and waits for completion before allowing it to close. A
save already committing may complete; its final status is authoritative. The
save dialog holds the package context stable while the shell remains responsive.
Activity history records completion, warnings, cancellation, and failure.

After saving, the package browser, asset browsers, level preview context, recent
files, and document-watch baseline use the saved output. If output reopening
fails after a committed in-place write, the stale archive reader is disabled and
the failure is reported. The saved package and backup remain on disk.
Reopening has its own byte progress and must match the writer's output SHA-256.
A different valid archive written by another process is not adopted as the
saved result. Cancellation after commit cannot undo the completed save; the
dialog finishes reopening and reports the actual outcome.

Archive writers use verified 64 KiB source chunks. The incremental DEFLATE
encoder retains one 65,535-byte block and a 32 KiB dictionary. ZIP/PK3 first
measure compression and CRC, then read again to write either compressed or
stored content; the passes must agree on content and sizes. This costs a second
read/compression pass but avoids a whole-entry buffer or temporary payload spool.
PAK and WAD stream stored content directly. Dry runs execute the same writer
without creating package, spool or manifest files. Directory/plan/manifest
metadata and source chunk fingerprints still grow with entry/source counts;
this is a bounded payload path, not a constant-memory whole application.

Requested manifests hash entry streams before replacing an in-place source.
Generated-content operation records use the same cancellable chunk reader, even
when a later edit deleted that entry. Digest reuse does not hash a whole buffer
to find its cache key.
Unverifiable content blocks the save before publication. Failure to publish the
optional manifest file after a successful package commit remains a warning.

Saves reserve a unique sibling file, verify its size and SHA-256, then publish
complete bytes atomically. New outputs refuse a destination created by another
writer. Replacements keep the existing package readable until commit and copy
its verified original bytes before replacing it. The previous `.bak` stays in
place until the new package is installed. Both overwrite modes preserve a backup.
Destination and backup checks use full content hashes, including when size and
modification time have not changed. Cooperating VibeStudio saves and recovery
operations lock the destination. External programs do not honor this lock;
content checks cannot exclude a foreign write in the final check/commit window.

The JSON `outputCommitted` field distinguishes an installed package from a
failed attempt. A backup or manifest warning after commit does not mean the
package was left unchanged. `backupPath` names the verified original copy and
`recoveryPaths` names retained transaction files when finalization fails.

## Interrupted saves

Before publication, a save records a `.vibestudio-package-*.payload.json`
journal beside the destination. The journal identifies the verified replacement,
original recovery copy, requested backup and their SHA-256 hashes. Normal
completion removes transaction files. An interrupted save retains them for review.

Open **File > Recover Packages > Interrupted Saves…**. The chooser checks journal
metadata in known output folders, or a folder you select. Actual GUI and CLI
archive saves remember their output folder before writing; the latest 16 folders
persist across restarts. The current project and recent package folders also
participate in the GUI review. It does not recursively search drives. Choose a
folder explicitly for older saves, moved folders, or other studio tools that use
the same publication service.

Select **Verify Selected Save** to check the output, original, replacement and
backup with progress and cancellation. **Finish Reviewed Save…** becomes available
only for a verified installed replacement. It confirms the output and backup
paths, rechecks the reviewed journal checksum and file contents, then finishes
the backup and cleanup. **Choose External Backup…** requires the exact recorded
path when the backup is outside the output folder. **Open Current Output** uses
the normal package-opening workflow, including the unsaved-document guard.
Activity records completion and failures. Closing cancels and joins the worker;
a backup already published before cancellation remains, with retained transaction
files available for a fresh review and retry.

Discovery scans at most 32 explicit folders, 100,000 directory members and 256
journals. Each journal is at most 64 KiB. Invalid journals remain visible; missing
folders, limits and cancellation make the inventory incomplete. Discovery does
not hash payload files or acquire a save lock. Verification and finishing use the
same service in the GUI and CLI.

```sh
vibestudio --cli package interrupted-saves --directory ./build --json
vibestudio --cli package recover ./build/.vibestudio-package-ABC123.payload.json --json
vibestudio --cli package recover ./build/.vibestudio-package-ABC123.payload.json --expected-sha256 <journal-sha256> --finish --json
```

`interrupted-saves` defaults to the current directory; repeat `--directory` for
more folders. JSON returns `inventory` with `directories`, `journals`,
`journalSha256` review tokens, `visitedEntries`, `complete`, `truncated`,
`cancelled`, `errors`, and `payloadsVerified: false`. Exit `0` requires a complete,
valid metadata inventory; `2` denotes invalid arguments and `4` an incomplete or
invalid inventory. It does not update preferences. Optional `--expected-sha256`
on `recover` rejects any journal change since the review; the GUI always supplies
it. Existing CLI callers may omit it while retaining full file verification.

Inspection is read-only. `--finish` verifies that the replacement is already
installed, publishes the original backup when safe, and removes verified
transaction files. It refuses changed destinations, changed backups, unsafe
journal paths or altered recovery copies. If interruption happened before
commit, inspection reports `original`; both versions remain available for manual
review, and `--finish` does not install the pending replacement. No recovery
operation silently rolls back a package or overwrites subsequent user edits.

If an unfinished backup points outside the output directory, inspection reports
`requiresBackupConfirmation`. After reviewing that path, explicitly repeat it as
`--finish --backup <recorded-path>`; journal contents alone cannot authorize an
external write. The selected path must exactly match the recorded destination.

Exit `0` means successful inspection or completion; `2` means invalid arguments,
`3` a missing journal, and `4` invalid or unsafe recovery. JSON exposes `state`,
`canFinish`, `finished`, `journalSha256`, `cancelled`, `backupVerified`, the retained
paths and an error when recovery is refused. Pre-commit replacements and changed
outputs remain manual-review cases; the chooser exposes the retained paths. Tests
cover abrupt process termination before and after commit.
Power-loss durability, network filesystems and native macOS/Linux execution
remain separate release verification requirements.

## Extract files

**Extract** and **Extract All** copy selected entries or whole contents from
the current planned package to a chosen folder. The worker dialog shows the current file and
byte progress; cancel or close stops within a stored or DEFLATE file. Completed
files remain on disk, and the current uncommitted file is discarded. This is
per-file atomic publication, not an all-or-nothing directory transaction.

The shared GUI/CLI service preflights the entire selection before creating
directories or files. It refuses unsafe paths, symbolic links or junctions in
the output path, input archive/staged-file destinations, writes inside a source
folder, repeated or case-folded names, Unicode normalization collisions, and
files that also occupy a required directory path. `--overwrite` does not resolve
collisions between package members. When GUI selections collide, **Extraction
Paths** shows each source occurrence and proposes a separate relative output
path. Edit those paths before extracting; invalid paths and namespace collisions
disable Extract. Cancel leaves the request unchanged. The worker still checks
filesystem containment, links and source protection before writing. A single
selected repeated entry can keep its original filename.

The CLI accepts repeatable `--entry-index N`, with repeatable `--as <relative-path>`
in matching order. Either supply one output override per index or omit all
of them. Obtain indexes from the current `list --json` response; they can change
after editing or reopening another snapshot. Index selectors can be combined
with path/prefix selectors, but not with `--extract-all`. Unmapped collisions
report every conflicting index and write nothing for that selection.

Stored and DEFLATE entries stream through bounded buffers and are committed only
after their full size and checksum checks succeed. Existing outputs are skipped
unless CLI `--overwrite` is requested. New outputs use atomic publication that
refuses a file appearing during extraction. An explicit replacement checks the
existing file's captured hash again before an atomic commit. Extraction does
not create save-style `.bak` backups. Foreign filesystem changes in the final
check/commit window cannot be excluded by portable Qt path checks.

```sh
vibestudio --cli package extract ./mod.pk3 --output ./unpacked --entry scripts/mod.cfg --dry-run --json
vibestudio --cli package extract ./mod.pk3 --output ./unpacked --entry scripts/mod.cfg --json
vibestudio --cli package list ./maps.wad --json
# Use the actual entryIndex values returned by list for each THINGS occurrence.
vibestudio --cli package extract ./maps.wad --output ./unpacked --entry-index 2 --as map-one/THINGS --entry-index 3 --as map-two/THINGS --dry-run --json
```

With no selectors the CLI extracts all entries; an empty selector, unsupported
option, repeated single-value option, extra positional argument, or combining
selectors with `--extract-all` returns usage exit `2` before reading/writing.
`--entry` and `--extract-entry` are repeatable; `--entries` accepts a semicolon
list. Dry runs open and fingerprint the source, then preflight paths and
metadata without decoding payloads or creating output. Exit `1` reports
extraction failure, and `0` a successful
operation (which may have skipped existing files). JSON `bytesRead` counts
streamed payload bytes, `totalBytes` counts committed bytes, and each entry
includes its zero-based `entryIndex` and physical `sourceOrdinal` when available.

The core extractor accepts an immutable planned reader, including generated
assets. The GUI captures that revision before path review and extraction; a
changed document during path selection requires selecting the entries again.
Blocked plans fail before output.

## CLI review

```sh
vibestudio --cli package compare ./release-1.pk3 ./release-2.pk3 --json
vibestudio --cli package compare ./mod.pk3 --staged --add-file ./autoexec.cfg --as scripts/autoexec.cfg --json
vibestudio --cli package compare ./mod.pk3 --staged --rename textures/old.tga --to textures/new.tga --delete scripts/unused.cfg --json
```

Staged review accepts the same add, replace, rename, delete, and conflict-policy
options as `package stage` and `package save-as`, and writes nothing. Its JSON
includes the comparison and staging manifest. Pass either a second package path
or `--staged`. Import, replacement, and rename pairs follow the existing staging
order: folder creation, additions, replacements, file renames, folder renames,
file deletions, then folder deletions.

Exit `0` means a complete match; exit `4` means differences, unchecked content,
reader warnings, or staging blockers. Missing/invalid arguments return `2`;
packages that cannot be opened return `3`. `--max-entry-bytes` must be positive.
`--metadata-only` limits the comparison to names and sizes. Opening still reads
the complete source files to capture their identities.

## Integrity validation

Choose **Packages > Validate** or run:

```sh
vibestudio --cli package validate ./release.pk3 --json
vibestudio --cli package validate ./release.pk3 --max-entry-bytes 536870912 --json
```

Validation reads every source file, including each occurrence of a repeated WAD
lump. It checks complete payload sizes, ZIP CRC-32, decompression, and local
header consistency, and records a SHA-256 hash for each verified entry. Stored
and DEFLATE payloads use bounded streaming buffers. Unsupported encryption or
compression fails validation explicitly. This checks package integrity, not
asset-format correctness or compatibility with a particular game.

After payload checks pass, validation verifies the captured source identity,
including container headers and directory records or folder membership. This
also checks empty packages. JSON separates payload `bytesRead` from
`sourceBytesRead` and reports `sourceVerified`. Optional byte budgets apply to
payload validation; opening still fingerprints the complete source.

The GUI shows progress and supports cancellation within a file and JSON export.
The CLI has no default per-entry byte limit; an optional positive
`--max-entry-bytes` leaves larger entries unchecked. Exit `0` requires every
file to verify with no loader warnings. Failures, warnings, and unchecked files
return `4`; invalid arguments return `2`, a missing input returns `3`, and an
unopenable archive returns `1`. JSON includes completion/cancellation, counts,
individual outcomes, physical source ordinals, hashes, and reader warnings.
The legacy `validation.usable` field now reflects the complete integrity result.

## Comparison coverage and remaining gaps

Names pair case-insensitively, with case-only changes reported separately.
Equal-sized members are read and hashed with SHA-256; ZIP directory checksums
alone never establish equality. Size differences need no payload read, so use
Validate to check every file's integrity. Archive, draft, imported and generated
plan entries share bounded streaming reads with cancellation within a file.
Unsupported stream readers and streams whose size disagrees with the directory
remain unchecked. By default an equal-sized member over 256 MiB remains
unchecked; this is an I/O budget, not a whole-file allocation limit. Repeated
WAD lump names pair by occurrence and read their own
physical entries. `completed` describes whether traversal completed, not whether every
entry was verified; inspect `uncomparedCount` and `identical` as well.

Plans own generated bytes and imported working copies, and retain their base
reader identities.
Compressed prefix previews stop inflation after collecting the requested bytes.
The `truncated` state means the unseen tail's decoded length and entry CRC have
not been verified; Validate or a complete read checks the entire entry. Image
imports require complete payloads and reject entries over 64 MiB before inflation.
Opening or staging a disk file captures its SHA-256 and a hash for each 64 KiB
chunk. Reads verify chunks before returning bytes, including capped previews
and PAK/WAD entries without format checksums. Changes that preserve size and
timestamps are detected. Accepted imports read their independent copies; changes
to an original import cannot alter the plan. A damaged working copy blocks reads
or publication. Saves still verify base content and retained bytes before writing
and publication; changed base-folder membership also blocks saving. Reopen a
changed base or restage damaged imported content. Recalculating the plan never
adopts new file content.

Fingerprints cost 32 bytes per 64 KiB plus per-file metadata; imported payloads
occupy independent temporary files. Neither protects against external programs
changing the backing storage.
Independent readers hold their own handles and one verified chunk buffer.
Staging manifests include captured file sizes, timestamps and SHA-256 hashes;
they are reports, not resumable editing sessions. File operations report
`contentStorage` as `owned-temporary` or `verified-file`. The original source path
and logical timestamp remain stable in these reports.

CLI `package stage`, `package manifest`, staged comparison, and all `--dry-run`
imports use explicitly verified source references without creating working copies.
They still detect source changes during their short-lived checks. Actual create,
draft-save and save-as imports use independent working copies. This keeps no-write
CLI inspection usable even when temporary storage is unavailable.

Loader warnings about skipped records block saving so
an unreadable record cannot disappear silently. Preserved duplicate PAK/ZIP
records remain advisory warnings, while valid repeated WAD names are normal.
Name-based edits that would choose among repeated entries are blocked and leave
every occurrence intact. Source-ordinal edits and mapped extraction keep each
occurrence separate. Archive subsets now preserve occurrence identity and expand
required WAD groups. Reviewed map/GL rename and complete group deletion now share
the staging service. New and opened WADs save their reviewed positional order;
full dependency-aware editing remains open.

Opening the editable document carries the same cancellation control through base
metadata, WAD directory reconstruction, ordering, snapshot rebasing and browser
admission. A failure preserves the current document, edits and Undo/Redo. Retained
row/text and plan allowances are checked before adding base rows or protected
input paths. WAD counts are checked before reserving directory storage, including
legacy metadata adapters. Concrete readers retain their exact source ordinals;
borrowed metadata pairing consumes each captured occurrence once. WAD previews
read the retained provider and honour the requested byte count, including zero. Subset preparation and save/reopen use
the same service. Cancelling adoption after a successful save does not undo the
committed output; the save result still reports it accurately.

The package inspector now prepares text/audio/model metadata on a coalescing
worker alongside its existing texture worker. Drag-export and other studio
preview handoffs still require a responsiveness audit. Internal plan preparation
has cancellation and row/text/key admission, and edit commits admit the projected
view. The entry list filters on a worker and materializes presentation on demand;
its native folder tree and composition share the prepared index. Base staging
now admits rows before growth and supports cancellation; remaining helper

synchronous GUI callers still need scale acceptance. Manifest metadata/JSON
serialization also remains open. Browsing

## Shared asset/workspace context

PK4 and PKZ filename aliases use the existing ZIP reader and its bounds and
compression checks. Texture DDS/FTX exports stage through the normal package
service; imported DDS/FTX/SWL pixels use the same preview decoder as the texture
editor. `asset formats` distinguishes decoding, native export and conversion
capabilities. [Portable workspaces](WORKSPACES.md) reference saved packages and
`.vibepackage` draft directories alongside map/code/asset selections; unsaved
staging still belongs to the package document and recovery workflow.

The workspace package section and the Levels Health texture check use the same
planned package as the browser. Staged additions, deletions, renames and
Undo/Redo refresh that context without reopening the map. Workspace counts
include staged entries and expose the staged-edit count. A refused planned view
reports its blocking reason instead of substituting original archive metadata.

Level texture checks run on immutable map/package snapshots in the background.
The Health tab shows progress, Cancel and Retry. A changed map or package cancels
obsolete work; only the latest requested context can publish results. Shader
reads stream with cancellation and bounded buffers, and a failed final integrity
check discards the buffered declarations. Incomplete reads, shader parsing,
collection limits or requested image decoding are explicit incomplete audits.
Partial counts cannot establish that all textures resolve. Known unreadable
image entries do not count as resolved, and a shader declaration takes precedence
over a same-named image, matching dependency export. A scan admits at most 64 MiB
of declared shader input, with the existing 16 MiB per-script and 4,096-script
limits; at most 128 diagnostics plus a truncation notice are retained. Reaching
these bounds is explicit and incomplete. Package sources are not modified.

`vibestudio --cli map textures ./maps/start.map --package ./work.vibepackage
--no-decode --json` reads the saved planned draft through the shared CLI package
loader. `textures.complete` and
`textures.cancelled` accompany the existing `sourceIndexComplete` field; an
incomplete audit or missing reference returns exit 4. Full dependency closure,
compiler handoffs and native accessibility/platform acceptance remain separate
release requirements.
