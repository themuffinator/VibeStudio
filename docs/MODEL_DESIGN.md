# Model Design And Level Handoff

For imported model geometry, component editing, and animation frames, see
[Editable Meshes](MODEL_MESH.md). **Edit as Mesh** bakes the current design into
that editor while retaining this separate parametric source.

After staging and placing a generated prop in a Quake III map, **Prepare Build
Workspace** captures that draft and the current map together. Compile the
snapshot, then **Publish Prepared Build** reviews the model/material assets and
verified compiler outputs as one PK3. The generated-model integration proof
checks this handoff through real q3map2, including external lightmaps and generated
shaders. **Deploy Prepared Build** carries the same model/material snapshot and
runtime outputs into a reviewed game folder; Build and Launch uses that review
after compilation. Recorder tests verify that the full package is present before
the executable starts. See [Prepared Builds](LEVEL_EDITOR.md#prepared-builds-with-current-assets).

Prepared Quake II builds also capture MD2 props and their resolved PCX skins
with WAL textures and sounds, then publish the verified BSP/assets as one PAK.
The generated ericw-tools proof checks each payload independently; it does not
establish runtime behavior of game-specific entity classes. Quake/Quake II
prepared installation deployment remains separate acceptance work.

**Models > Design Prop** creates static props from box, cylinder, and plane
parts. Each part has dimensions, an origin, rotation about all three axes, an
image or Quake III shader path, and a UV transform. Cylinders have 3–64 segments;
unrotated planes face +Z. The preview uses the existing software model viewport.
Select a part in the preview or the keyboard-accessible parts list; its surface
is hatched (or uses a thick dashed wire outline) and its name is shown below the preview. Parts can be added,
duplicated, removed, and edited with a 100-step undo/redo history that restores
the selected part. Undoing back to the saved design clears the modified state.
A design contains at most 32 parts. Closing a modified design offers Save,
Discard, and Cancel.

The **Part** tab holds dimensions, position, and X/Y/Z rotation. **Surface** holds
the material path and UV scale, offset, and rotation. Negative UV scale mirrors
a texture; **Reset UVs** restores the default mapping in one undo step. Choose
**UV checker** above the preview to inspect tiling and orientation with a generated
checker, or use **Solid** and **Wireframe**. **Handoff** holds the package path,
replacement setting, and level placement. All tabs have scrollable properties.

## One Asset Through The Studio

1. Open the project asset folder or package. Open a Quake III map for placement.
2. Open **Design Prop**, assemble the parts, and set material paths from your
   project. **Show Material** follows a material into the existing
   texture surface. The authoring preview offers solid, wireframe, and UV checker
   modes; it does not resolve project material images or render shaders.
3. **Save Design** stores the editable source as `.model.json`. **Export MD3**
   writes a static game model; **Export OBJ** writes geometry for an external
   modeller. Export does not overwrite the design source.
4. Choose the package-relative model path. **Stage in Package** adds owned
   generated bytes to the package plan. Replacing a path requires the explicit
   **Replace existing entry** setting. No temporary model file is required.
5. **Stage and Place** also adds a `misc_model` entity at the specified level
   coordinates. This is one map undo step. A failed handoff changes neither the
   map nor the package plan. Map undo does not remove the staged asset: package
   operations remain separately reviewable and removable in Packages.
6. **Levels > Dependencies** audits the current staged plan, including generated
   models, replacements, renames, and deletions. MDL/MD2/MD3 material references
   lead to package images or Quake III shaders and their image dependencies.
   Missing assets or incomplete scans block dependency-subset export.
7. Review the package plan and save it; save the map separately. The compiler
   consumes saved files, so stage-and-place alone does not put the model into a
   compiler's search path. Export the dependency subset or the full staged
   package into your configured build/game asset layout before compiling.

Generated staged props appear in the Levels 3D preview and can be selected as
entities. The preview applies origin, `angle`/`angles`, and
`modelscale`/`modelscale_vec`, and shares the map triangle budget. It decodes
static frame-zero models through the shared material resolver, including folder,
package and staged readers. Default preview limits are 32 model paths, 16 MiB per
entry and 64 MiB total asset reads; unavailable assets are reported. Reopened
package models also remain available through the Models browser.

Placed models can be captured with brushes, patches and connected entities in
[Reusable Prefabs](LEVEL_EDITOR.md#reusable-prefabs). Their model paths and
orientation stay in the assembly, and placement uses the shared model preview
and dependency readers. Prefabs reference exported model assets; editable
`.model.json` source remains a separate authoring document. The prefab does not
embed the model or automatically publish assets into compiler search paths.

## Editable Source And Export Boundaries

New saves use schema version 2. Version 1 designs still load with zero roll and
pitch and identity UV mapping. Older VibeStudio versions reject version 2 instead
of silently losing transforms. See [the version 1 pillar](../samples/models/pillar.model.json)
and [the version 2 angled panel](../samples/models/angled-panel.model.json) for
complete examples. Their material paths must be supplied by the project; no
commercial assets are included.

- `name`: 1–48 ASCII letters, digits, underscores, or hyphens.
- `parts`: 1–32 objects with unique names, `primitive` (`box`, `cylinder`,
  `plane`), `size` and `origin` XYZ arrays, numeric `yaw`, integer `segments`,
  and a package-relative `material` path of at most 63 ASCII characters.
- Version 2 parts additionally require numeric `roll`, `pitch`, and `uvRotation`,
  plus `uvScale` and `uvOffset` UV pairs. Identity values are `0`, `0`, `0`,
  `[1, 1]`, and `[0, 0]` respectively. Partial or malformed transforms are rejected.
- Coordinates use level units, with Z up. Dimensions are 1/64–1000 units;
  origins are within ±10000 and rotations within ±36000 degrees. Scale local
  geometry by dimensions, rotate about X (roll), then Y (pitch), then Z (yaw),
  and translate to the part origin. Normals follow the same rotations after
  inverse-scale correction. Input files are limited to 1 MiB. A failed load
  preserves the current design.
- UVs are scaled about `[0, 0]`, then rotated about `[0, 0]`, then offset.
  Scale magnitudes are 1/64–64, with negative values allowed for mirroring;
  offsets are within ±1024. U goes right and V goes down the image, so positive
  UV rotation is clockwise in image space. Values outside `[0, 1]` repeat in the
  checker preview and are retained in MD3. OBJ converts V to its bottom-up
  convention. UV edits apply to a whole part; vertex-level unwrapping is deferred.
- MD3 export writes one frame and one surface per part, with UVs, packed
  normals, and material names. Coordinates are rounded to 1/64 unit and must
  fit -512 through 511.984375. Export refuses overflowing coordinates or
  triangles that collapse at that precision. MD3 does not store the editable
  primitive parameters.
- OBJ retains part groups, normals, UVs, and material names; it does not create
  an MTL companion or embed images. Neither exporter writes animation, bones,
  tags, collisions, LODs, or edited versions of imported native models.
- Intersecting parts are separate surfaces, not a boolean union. The software
  preview uses triangle sorting without a depth buffer, so intersections can
  display incorrectly. The MD3 still contains the authored geometry.

## CLI Workflow

```sh
vibestudio --cli model build ./samples/models/pillar.model.json --output ./out/pillar.md3 --dry-run --json
vibestudio --cli model build ./samples/models/pillar.model.json --output ./out/pillar.md3
vibestudio --cli package save-as ./assets ./out/props.pk3 --add-file ./out/pillar.md3 --as models/props/pillar.md3
vibestudio --cli map place-model ./maps/arena.map --engine idTech3 --package ./out/props.pk3 --entry models/props/pillar.md3 --origin 64,0,0 --output ./out/arena.map
vibestudio --cli map dependencies ./out/arena.map --engine idTech3 --package ./out/props.pk3 --json
```

The build and placement commands share the GUI's services. `model build`
accepts `--format md3|obj` or infers it from the output extension. `--dry-run`
creates no output directories; existing outputs require `--overwrite`.
`map place-model` requires a readable, unambiguous MD3 entry no larger than
8 MiB, without parser warnings, and saves through the normal map save-as service.
WAD model staging and non-Quake-III placement are refused.

Dependency scans read at most 128 models, 8 MiB per model, and 64 MiB total.
Unsupported or malformed model data makes the audit incomplete. External
`.skin` overrides, secondary shader links, dynamic game assets, and Doom
composite texture groups still need separate review. A package-plan snapshot
owns generated bytes; files on disk remain lazy reads and should not be changed
while an export is running.
