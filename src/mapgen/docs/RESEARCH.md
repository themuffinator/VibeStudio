# Research and technical decisions

Research was checked against primary upstream sources and the locally available reference trees on 26 August 2026. Exact dependency/tool pins and licence boundaries are recorded in [THIRD_PARTY.md](../THIRD_PARTY.md).

## ggml and prompt inference

[ggml](https://github.com/ggml-org/ggml) supplies the tensor graph used by the deterministic candidate ranker. GGUF is a model container, not an architecture-independent inference engine: tokenizer, tensor mapping, decode graph, KV cache, chat formatting, and sampling still need a model implementation.

The project therefore pins [llama.cpp v0.3.0](https://github.com/ggml-org/llama.cpp/releases/tag/v0.3.0), with synchronized ggml v0.22.0, behind project-owned `TextModel` and ranking boundaries. The reference contracts are the upstream [public llama API](https://github.com/ggml-org/llama.cpp/blob/v0.3.0/include/llama.h), [GGUF specification](https://github.com/ggml-org/ggml/blob/v0.22.0/docs/gguf.md), and [release synchronization policy](https://github.com/ggml-org/ggml/discussions/1579).

The adapter accepts one explicit decoder-only GGUF with a supported embedded chat template, defaults to CPU-only deterministic inference, applies grammar before greedy sampling, and creates a fresh bounded context per attempt. Split GGUFs are rejected because a single-shard hash would misstate provenance. A double streaming SHA-256 check detects a model file changing across load.

Exact load/template/tokenize/grammar/decode/report behavior was exercised with the external Apache-2.0 [SmolLM2-135M-Instruct Q8_0 quant](https://huggingface.co/unsloth/SmolLM2-135M-Instruct-GGUF/blob/9e6855bc4be717fca1ef21360a1db4b29d5c559a/SmolLM2-135M-Instruct-Q8_0.gguf), pinned locally by SHA-256 `c4a3dd037301b6ecea31d6da37f5cd793ead920dd5ddfe6d589294628d6ce66a`. It remains an unbundled test input. Because tokenizer metadata is embedded in the same GGUF, the report records the whole-file digest as tokenizer-source identity rather than claiming a tokenizer-only hash.

## Title and source-format distinctions

- Quake SP needs authored progression, combat/resources, vertical traversal, and a reachable exit; MP needs redundant routes, spawn safety, item control, and readable sightlines.
- Quake II has similar high-level modes but different entity contracts, liquid contents, surface metadata, movement/gameplay values, and CTF conventions.
- Quake III Arena is arena-first. Its “single-player” is tournament play over multiplayer arenas. Bot compilation produces AAS; there is no stock Q1/Q2-style monster campaign or general stock changelevel entity to invent.

Behavior and binary envelopes are checked against the official [Quake](https://github.com/id-Software/Quake), [Quake II](https://github.com/id-Software/Quake-2), and [Quake III Arena](https://github.com/id-Software/Quake-III-Arena) source releases.

M3 movement profiles were checked more narrowly against Quake’s [BSP hulls](https://github.com/id-Software/Quake/blob/master/QW/server/model.c), [18-unit ground step](https://github.com/id-Software/Quake/blob/master/QW/server/sv_move.c), and [default gravity](https://github.com/id-Software/Quake/blob/master/QW/server/sv_phys.c); Quake II’s [player hull/jump/gravity/step movement](https://github.com/id-Software/Quake-2/blob/master/qcommon/pmove.c), [ground-monster stepping](https://github.com/id-Software/Quake-2/blob/master/game/m_move.c), and representative [large monster hull](https://github.com/id-Software/Quake-2/blob/master/game/m_gladiator.c); and Quake III’s [player hull](https://github.com/id-Software/Quake-III-Arena/blob/master/code/game/bg_pmove.c), [step/jump constants](https://github.com/id-Software/Quake-III-Arena/blob/master/code/game/bg_local.h), and [default gravity](https://github.com/id-Software/Quake-III-Arena/blob/master/code/game/bg_public.h). The project uses those behavioral constants to define conservative planning profiles; it does not port engine movement code or claim frame-exact simulation.

For editable source syntax, the exact reviewed references are the ericw-tools [map parser and Valve 220 handling](https://github.com/ericwa/ericw-tools/blob/8b70fce25558f2662ebee0855c12d35fe21e7beb/common/mapfile.cc), the NetRadiant Custom [q3map2 parser](https://github.com/Garux/netradiant-custom/blob/449778b3840f8f2062daab15c87cb012f2ac945c/tools/quake3/q3map2/map.cpp), and its [Radiant brush-token model](https://github.com/Garux/netradiant-custom/blob/449778b3840f8f2062daab15c87cb012f2ac945c/radiant/brushtokens.h). They support the following M2 decisions:

- Q1/Q2 generation uses explicit Valve 220 axes and `mapversion 220` rather than the old bootstrap projection.
- Q2 contents/surface/value is optional source syntax and must preserve both presence and absence; generated non-solid liquids use water 32, slime 16, and lava 8.
- Q3 legacy and brush-primitive brushes are distinct dialects. A generated document does not mix their brush models.
- Q3 material names supplied to q3map2 are relative to `textures/`; pre-prefixing creates the invalid `textures/textures/...` path.
- Q3 generated faces carry explicit contents/surface/value, and detail ownership is consistent across a whole brush.
- `patchDef2` retains odd width-major control grids within the portable 3–31 bound.

No GPL parser, compiler, entity, or game-source implementation was copied. The MIT code was written against the observed contracts and is protected by canonical goldens plus external compiler tests.

## Free-space and representation decisions

Treating every room as an independent six-sided shell cannot correctly express arbitrary overlapping openings: a later portal can reseal an earlier wall fragment, and global wrapping hides responsibility. M2 instead defines rooms/passages as free-space boxes and derives only the exposed boundary of their union. Coordinate compression makes partial openings, T/cross junctions, duplicates, and contained volumes explicit while allowing hard caps before combinatorial work grows unbounded.

The same separation motivated two IRs. `Layout` owns integer topology, convex geometry, typed contents/ownership, and stable semantic IDs. `MapDocument` owns ordered epairs, brush projections, optional metadata, patches, and stable syntax-node IDs. A syntax-preserving profile can retain legacy source distinctions; a stricter generated profile prevents the generator from inventing ambiguous ones.

Curves also need two representations. Q1/Q2 consume segmented convex wall brushes. Q3 can add a `patchDef2` veneer, but the patch is not collision geometry, so the construction result retains explicit hidden convex backing. Integer control positions and fixed-point UV units keep construction deterministic until dialect lowering.

## Static analysis and localized repair decisions

A usable navigation graph needs title hull clearance, not a room-center adjacency graph. M3 therefore expands obstacles against a selected player or Q1/Q2 ground-monster hull, coordinate-compresses legal origin space, and retains stable room/connection/solid/placement source references on nodes and transitions. Natural edges are limited to bounded walk, step, jump, and drop tests; door, lift, and teleporter edges require the existing typed placement/link contracts. The result is deterministic planning evidence, not a replacement for engine physics or bot/monster AI.

Visibility similarly operates on the exact room/passage free-space union. Box solids can be exact segment occluders; arbitrary validated convex solids currently use their aggregate bounds, so affected results explicitly carry `conservative` precision rather than overstating exactness. Conservative bounds are treated as potentially visible: they cannot prove hostile occlusion, cover, or safety, and required missing cover participates in the spawn `safe` verdict when that check is enabled. Integer geometry and CORDIC angles avoid platform-dependent trigonometric ordering in exposure, cover, crossfire, articulation, chokepoint, and spawn-safety metrics.

The analytical lighting metric exists to make dark critical placements and unreadable/high-contrast passages discoverable before an expensive compiler pass. It deduplicates repeated passage boxes, batches all sample/light visibility traces once, cross-validates its caps against the nested visibility limits, and uses deterministic integer intensity/color/attenuation arithmetic. It is not physical lux and does not predict every compiler feature; compiled lightmap/lit/light-grid gates remain independent evidence.

Compiler leak trails are normalized evidence rather than trusted edits. The pinned ericw-tools [outside-fill implementation](https://github.com/ericwa/ericw-tools/blob/8b70fce25558f2662ebee0855c12d35fe21e7beb/qbsp/outside.cc) writes classic coordinate trails as `.pts`, while the pinned q3map2 [leak writer](https://github.com/Garux/netradiant-custom/blob/449778b3840f8f2062daab15c87cb012f2ac945c/tools/quake3/q3map2/leakfile.cpp) writes `.lin`; Radiant’s [reader](https://github.com/Garux/netradiant-custom/blob/449778b3840f8f2062daab15c87cb012f2ac945c/radiant/points.cpp) recognizes both conventions. M3 parses strict finite triplets under byte/line/point/coordinate caps, converts them to 1/1024-unit fixed point, removes adjacent duplicates, and makes forward/reverse traversal share a fingerprint. It does not copy compiler tracing code.

For diagnosis, a coordinate-compressed flood classifies exterior, enclosed void, and playable interior around the exact `Layout` free-space union. Only a unique first exposed-face crossing with one room/connection owner and an independently locatable exterior cell can produce a proposal. Ambiguous edge/corner/coincident crossings produce no edit. The proposal is a bounded local slab attached to that owner and carries canonical layout SHA-256 plus precondition and regression metadata that becomes stale when the layout or witness changes; it never wraps the whole map. `local_seal_proposal_preconditions_hold` proves only that this local applicability metadata still matches, not that compiler output is sealed.

Quality findings are observations until an acceptance policy consumes them, although analyzer execution and resource caps remain mandatory fail-closed pipeline stages. Every supplied navigation, visibility, lighting, or leak artifact must carry the exact lowercase SHA-256 of the canonical typed `Layout`. `QualityAnalyzer` also independently reruns the supplied analyzers under the exact `QualityOptions` and requires full typed-content equality; a null leak means not evaluated, while a supplied non-diagnosed result rejects. `QualityAnalysis` repeats the layout SHA, and report rendering independently recomputes and content-compares an available quality artifact before JSON serialization. The reorder-invariant 64-bit quality fingerprint is only a lightweight edit precondition. The M3 quality policy is explicit and deterministic: compare structural, leak, navigation, visibility, lighting, timing, then warning counts lexicographically; reject stale preconditions, new structural errors, placement identity loss, path loss, any new or substituted navigation-error identity, incompatible repair dialect, or lowering failure; and accept only a strict improvement. `QualityRepairOptions::dialect` can bind lowering to an exact title-compatible dialect—including Q3 brush primitives—or use the title default, and a supplied construction result preserves patch veneers and mover directives through candidate lowering.

A seal has an additional non-negotiable condition: configured `CompilerRecheckRequirements` identify a runner policy, exact map and pointfile dialects, and compiler executable/options/invocation hashes. Matching `CompilerRecheckEvidence` binds the envelope schema, runner, proposal, baseline and candidate fingerprints and canonical layout hashes, canonical lowered map hash/bytes, BSP hash/bytes, diagnostics hash, pointfile witness/dialect, compiler success, postcompile pointfile absence, and explicit leak-free result. `compiler_recheck_envelope_sha256` is an unkeyed, size-capped field-integrity digest and explicitly not authentication. A non-null host `CompilerRecheckVerifier` must authenticate its opaque payload through a signature, trusted IPC token, or other out-of-process trust mechanism and return true. Missing, mismatched, oversized, false, or throwing verification rejects; core supplies neither key management nor automatic compiler execution, and an in-memory flood result alone is never proof.

## Compiler strategy and evidence

[ericw-tools](https://github.com/ericwa/ericw-tools) is invoked as an external compiler process. M2/M3 used clean source revision [`8b70fce25558f2662ebee0855c12d35fe21e7beb`](https://github.com/ericwa/ericw-tools/commit/8b70fce25558f2662ebee0855c12d35fe21e7beb) and separately installed 2.0.0-alpha11 artifacts: `qbsp` SHA-256 `fad5a4dc4daf42773ad9a812349b2667221bec47a920cad10cb821ae442c8eb8`, `vis` SHA-256 `01be572845e05c87b01a0b667e590ac49bdaba23369af8529fe82fcfbc4fe6cf`, and `light` SHA-256 `8e4fe9821f73c2d5c8a13655be20d3a71f357e76171de37c02413f4da3131a2f`. CMake requires each enabled tool to be caller-supplied and hash-matched. The Q1/Q2 matrices use leak testing, forbid automatic BSP upgrades, inspect required lumps, require nonempty portal files, and reject both `.pts` and `.lin` plus known invalid-brush diagnostics. Project-authored open-ceiling negative controls must produce leak diagnostics and nonempty `.pts`. Every SP and 32-room MP/CTF fixture runs quick and final VIS/light when the complete optional quartet is configured. These stages run single-threaded where supported; no byte-for-byte compiler artifact determinism is claimed. VIS and lighting lumps must be nonempty; Q1 also requires a QLIT v1 sidecar with the exact RGB payload size implied by BSP samples. Compiler evidence remains necessary: the original gate caught brush point winding that plausible in-memory bounds did not.

Q3 validation uses external [NetRadiant Custom](https://github.com/Garux/netradiant-custom) tools from clean revision [`449778b3840f8f2062daab15c87cb012f2ac945c`](https://github.com/Garux/netradiant-custom/commit/449778b3840f8f2062daab15c87cb012f2ac945c). The tested `q3map2` SHA-256 is `7cc3963b21fa937880935e818624eb28c5424f7ff312148b13468e7afb1a71e7`; the tested `mbspc` SHA-256 is `77c9b9cac946e7d770bce9d934404b421e51ebe01963cd864c9d0e245243b003`. CMake requires callers to provide both expected hashes and the separate runtime-library directory.

Q3 tests run in private base/home/work/AAS roots with small project-authored test shaders, so no commercial assets are required or copied. Both brush dialects independently compile duel, CTF, and 32-room DM maps to IBSP46 and EAAS5. Every scale receives single-threaded quick VIS/light and the duel representative also receives final VIS/light; every lit stage must report positive illuminated luxels and lightmaps, while surface, lightmap, light-grid, and visibility lumps remain nonempty. The EAAS5 unprotected envelope is checked directly. Its version-5 checksum/lump-table payload is protected, so semantic content is validated through the already pinned BSPC `-aasinfo` reader rather than copying a GPL decoder into this repository. The gate requires positive and consistent area/settings, reachability-size, node, portal, and cluster counts, complete reachability-category accounting, and representative positive walk/barrier-jump/walk-off-ledge evidence. That is global compiled topology/category evidence; entity-to-entity reachability comes from the project navigation analyzer. A deliberately open-ceiling map in each native Q3 brush dialect must leak and emit `.lin`, making the negative control independent of compiler exit-code conventions.

ericw-tools and NetRadiant Custom remain separate GPL processes. Their executables, runtime libraries, source/build trees, logs, and outputs are not linked into or redistributed with this MIT project.

## Local corpus findings

The local reference store contains many Q1/Q2/Q3 BSPs and Q3 AAS files, but most are commercial data suitable only for local black-box compatibility checks. The ericw tree contains compiler fixtures, not a blanket-clean training corpus. One file named `Q2/sound/misc/bigtele.map` is RIFF/WAVE data, demonstrating that future ingestion must validate signatures rather than trust extensions.

No commercial or community map is copied into this repository. Dataset admission still requires explicit provenance and licence review as described in [DATASET.md](DATASET.md).
